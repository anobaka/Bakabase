集合与获取流水线设计

范围：从「我想要这个作品」到「它成为库里一个带完整元数据的资源」的整条链路，以及跨来源的集合、收集率与订阅补全。首个落地场景是从论坛人工下载的 galgame 与小型单机游戏，但每一层都按漫画、同人本、同人音声、电影、电视剧同样适用来设计。

全文的现状结论均已在代码中逐条核实，引用格式为 仓库相对路径:行号（行号随代码演进可能漂移，以文件与成员名为准）。术语一律使用代码中的实际标识符，不使用自造缩写。标签含义：现有 代码里已经存在；需修正 存在但要改；新增 本方案引入；后期 明确排到后面的阶段；待定 需要实际数据或产品决定。

一句话结论

「我还没有的作品」就是尚未落地的资源：一条 Resource，Path 为空，身份由 ResourceSourceLink 的 (Source, SourceKey) 给出。代码里这种资源今天已经存在（未安装的 Steam 游戏、未下载的 DLsite 作品），本方案只是把它从三个站点的私有实现推广为通用机制。

四层拆分，自下而上

未落地资源是地基：不依赖任何集合就能创建、查看、获取、关联，「我缺了哪个资源」在这一层就能表达。获取流水线以一个未落地资源为目标，按它自带的获取线索（帖子链接、直链、某个外部身份）选一份获取方案（可编排、可替换的步骤序列，由 Workflow 引擎承载），把它变成已落地资源。集合是资源（含未落地资源）的命名分组，收集率 = 已落地成员 ÷ 全部成员。订阅是集合的外部真相源，负责告诉集合「应该有哪些条目」。

先做什么

第一阶段把未落地资源做成独立可用的概念：手动创建、按「未落地」筛选、关联本地目录、卡片与详情的状态表现。第二阶段做「收件箱版」获取流水线：帖子解析 → 打开链接 → 用户把文件丢进收件箱 → 自动认领、解压、按模板放置、落地。两期都不需要集合，却直接消灭当前人工流程里五步中的四步。

  • 不引入与 Resource 割裂的新概念。「作品」不是新实体，就是资源；未拥有的作品是尚未落地的资源。

  • 获取以资源为目标。每个获取任务补齐的是一个具体的资源，用什么方式由该资源的获取线索决定；集合、订阅只是发起获取的场景之一。
  • 平台持有与分享获取是两种独立机制。只有持有资源的平台（以及定义作品身份的元数据库）才能成为资源的外部身份 ResourceSourceLink；论坛、推文、文档、表格这类分享渠道永远不写入身份，只提供获取线索。

  • 迁移一律由 dotnet ef migrations add 生成，纯 schema。需要搬运存量数据时用运行时的一次性迁移器（先例：src/legacy/Bakabase.Migrations/V230/PathsRelocationMigrator.cs），且接受 beta 期的存量数据丢失。
  • 新功能优先进 src/modules/。只有与 legacy 紧耦合的小改动留在 src/legacy/。
  • 获取流程是动态的，先有抽象底层，再做可插拔实现。步骤契约与宿主无关；宿主是 Workflow 引擎的一次最小扩展（挂起 / 恢复 + 单条目游标），独立运行器作为备选宿主保留（§7.2）。引擎不加分支、循环或多条目挂起。

3.1 资源与外部事物的三种关系

所有「来源」按它与资源的关系分成三类。这个分类决定了一个外部事物能不能成为资源的身份、能不能取回文件、以及在代码里用什么表示。分类是本方案最重要的边界之一，后文的订阅提供器、线索种类、对接器都按它划分。

§4尚未落地的资源

这一节把「资源可以没有本地路径」从三个站点的隐含行为变成明确的、有统一入口、不依赖集合就能独立使用的机制。它是获取流水线与集合共同依赖的地基，因此排在第一阶段交付（§13）。

4.1 表示方式

  • 存储不变。ResourceDbModel.Path 继续可空；不新增「虚拟资源」表。
  • 领域模型加一个只读判定。Resource.HasLocalPath => !string.IsNullOrEmpty(Path)。当前散落在后端至少 20 余处、前端数处的 !string.IsNullOrEmpty(resource.Path) / !!resource.path 统一改为读它（清单见 §4.3）。
  • 加一个内部属性 InternalProperty.HasLocalPath（Boolean），值从 Path 派生，按 .claude/rules/adding-builtin-property.md 的清单接入枚举、PropertyInternals、索引、legacy 回退搜索、前端常量。它给筛选面板一个直白的「已落地 / 未落地」开关，替代目前只有内行才知道的 Filename IsNull 写法。索引更新走现有的资源变更事件（IResourceDataChangeEventPublisher.PublishResourcesChanged），落地服务必须发布该事件。
  • ResourceStatus 保持原义。它表示「外部来源是否仍列出该条目」（Active / Absent），与是否落地正交：一个未安装的 Steam 游戏是 Active 且未落地；一个从社团页消失但本地仍有文件的作品是 Absent 且已落地。Unavailable 至今无人赋值，本方案不使用它。
  • 名称。未落地资源的显示名来自保留属性 Name，由订阅或获取任务在创建时写入（§6.2）。当前 ResourceSyncService.PopulateResourceNames 对虚拟条目按路径查找资源因此永远查不到（ResourceSyncService.cs:460-467），要改为按 (Source, SourceKey) 查找。

5.2 收集率

收集率 = 已落地且未忽略的成员数 ÷ 未忽略的成员数。「忽略」是成员级标记（CollectionResourceMapping.IsIgnored），表示「我知道它存在但不打算收」，只对落表的成员可设。

一个值得说清楚的推论：收集率只在集合里存在未落地成员时才有信息量。纯手动加入已有资源的集合恒为 100%；纯规则集合通常也接近 100%，除非规则命中了其他订阅带进来的未落地资源。所以「有收集率」这个能力实质上等于「有外部真相源」，也就是订阅（§6）。集合页在收集率旁边给出成员构成（已落地 / 未落地 / 获取中 / 已忽略）比一个百分比更有用。

5.3 逐条回答：层级、管理、能力、关联、搜索

要不要多层级

不做树形集合实体。系列内部的层级（物语系列 / 伤物语）用 Multilevel 属性表达，这是 09-collections 已收敛的决定；「作者 + 系列」这类组合用规则表达。集合页提供「按某个属性分组显示成员」（例如按系列属性分组），视觉上得到层级，数据上不引入父子集合。理由：树形集合带来排序继承、循环、跨树移动等一整套边界问题，而两种既有机制已覆盖需求。

如何管理

集合页（列表）+ 集合详情页（成员 / 来源 / 规则 / 设置四个标签）。成员支持：排序（手动顺序，用于系列顺序）、忽略、移出、批量获取、按状态筛选。集合本身支持：颜色、封面（取成员封面拼图或手动指定）、描述、自动获取开关、获取设置覆盖。

有什么能力

  • 显示收集率与成员构成
  • 一键「获取缺失条目」（§7）
  • 订阅检查 → 通知 + Workflow 事件（§6）
  • 「在资源页打开」：把集合转成资源筛选（CollectionMulti In [id]）
  • 从 Multilevel 节点、从外部编号、从现有筛选一键创建
  • 成员为未落地资源时，其外部身份的元数据可通过增强器补属性（DLsite / Bangumi 增强器已能按名称或编号工作，见 §4.3 的关键词回退）

如何关联资源

落表成员用 CollectionResourceMapping (CollectionId, ResourceId)，与媒体库的 MediaLibraryResourceMappingDbModel 同构。规则成员不落表。一个资源属于多个集合天然成立。资源详情有「所属集合」块（克隆 DetailModal/MediaLibraryMappings）。

如何搜索

新增内部属性 ResourceProperty.CollectionMulti = 29（MultipleChoice，选项 = 集合列表），完全照抄 MediaLibraryV2Multi 的接入方式（§5.5）。索引里每个集合 id 一个键；规则成员在索引构建/资源变更时一并计算写入，因此搜索「在集合 X 里」对三种来路一致。

与 ResourceProfile / SavedSearch 的关系

规则集合的 RuleSearchJson 与 ResourceProfileDbModel.SearchJson 同一模型，评估复用 IResourceProfileService.GetMatchingResourceIdsBySearchJson，编辑器复用 ResourceFilterController。不复用 SavedSearch（它是可变的标签页状态）。ResourceProfile 继续只承载配置，不承载浏览。

5.4 自动把识别到的资源放进集合

「识别」在这里有三种确定性递减的方式，方案按顺序采用：

  1. 获取流水线自带身份。从订阅条目发起的获取任务知道自己对应哪个未落地资源，落地后成员资格不变，无需识别。这是最常见的路径，也是把身份匹配问题绕开的关键。
  2. 按外部编号匹配。存量库里的 ResourceSourceLink 今天由来源同步（ResourceSyncService.ResolveResourceForEntry / EnsureSourceLink）与解析器的迁移候选写入；增强器（含 DLsite、ExHentai、Bangumi）都不写链接，也没有 Steam 增强器。方案给关键词增强器在命中后增加写入链接的逻辑（DLsite 命中 RJ 号、Bangumi 命中条目 id 时 EnsureLinks），订阅检查时按 (Source, SourceKey) 找到已有资源就直接加入集合，不新建未落地资源。目录扫描也走同一逻辑（DLsiteWorkService.ScanFolder 的 RJ 号正则提升为共享的 TryExtractSourceKey）。
  3. 按标题模糊匹配。用 ITextOps.Clean（精确一侧）与 TitleSimilarity（相近一侧）归一化后比对，命中进「待确认」列表（ResourceMatchSuggestion 表），用户确认后合并。沿用 docs/local-file-organization/modules/04-resolution.md 的保守默认：不自动合并。相似度为字符二元组的 Sørensen–Dice 系数（无空格的日文标题按词切分只会得到 0 或 1），阈值 0.82；两侧数字序列不一致的一律不提——同一系列的分卷字符几乎全同、只差表示第几卷的部分，正是分数最高又必然判错的一类。确认即把新资源的身份、线索与集合成员资格转移到已有资源上并删除新资源；只有未落地资源可被合并掉。拒绝会被记住，同一对不会再问第二次。
    只在按标题、按分享链接两条路径上计算（它们本就要扫一遍名称）；按外部身份创建不做标题匹配——身份就是身份，且为每个列出的作品扫全库名称会让一次两百件的社团页同步变得昂贵而无所得。

§6订阅：集合的外部来源

6.1 为什么订阅就是集合来源

现有 AbstractListIdDiffProvider.FetchCurrentItemsAsync 做的事——抓一份外部列表、按条目 id 求差——和「集合应该包含哪些条目」的采集是同一个操作。区别只有两点：订阅把结果存成一份滚动快照，集合需要把每一项持久化成资源并记住它属于哪个集合；订阅的差异是对上一份快照的，集合的差异是对已持久化成员的。把快照换成资源，订阅就成为集合来源，不需要第二套抓取框架。

决定：每个订阅属于一个集合。现有三个订阅在升级时由运行时一次性迁移器为各自创建同名集合；SubscriptionSnapshotDbModel 表停用（差异改为对成员表计算）。/subscription 页面保留为「所有订阅」的总览，编辑入口迁到集合详情的「来源」标签。

§7获取流水线：抽象底层与可编排方案

获取任务把「一个未落地资源」变成「已落地资源」。流程本身是动态的：不是所有资源都来自论坛，不是都经网盘，下载后不一定要解压，有的要重命名。因此本节先定义与任何宿主无关的抽象底层（步骤、工作项、方案、运行），再给出宿主（Workflow 引擎的一次最小扩展），最后把当前提出的具体流程做成几份可自由替换插拔的内置方案。

    List<AcquisitionLink> Links;  int? SelectedLinkIndex;   // 解析产物；AcquisitionLink { Url, AccessCode, ArchivePassword, DriveKind }
    string WorkingDirectory;  List<string> Files;            // 抓取或认领得到的文件
    string? ExtractedDirectory;               // 解压产物
    string WorkingText;                       // ITextWorkpiece：将要使用的目录名，现有 transform.text.* 节点可以直接改它
    string? TargetDirectory;                  // 放置产物
    Dictionary<string,string> Variables;   List<PurchaseRecord> Purchases;
}
  • 方案（recipe）= 有序的「步骤 Kind + 配置 JSON」列表，是数据。内置方案是只读种子，用户复制后自由改；一个资源、一个集合、一种线索都可以指定默认方案（§7.4）。
  • 运行= 一个目标资源 + 一份方案 + 当前步骤游标 + 工作项快照 + 状态（运行中 / 等待中 / 完成 / 失败 / 取消）+ 等待原因。每步结束即持久化，进程重启后从游标步骤续跑。
  • 幂等是步骤的义务：直链下载检查工作目录已有完整文件即跳过；放置检查目标目录已存在且内容一致即跳过。宿主重跑当前步骤时依赖这一点。
  • 这层与 docs/local-file-organization/foundations.md 的「组件 = 代码，实例 = 数据；内置皆种子，可复制」一致。

7.2 宿主：Workflow 引擎的最小扩展

宿主要提供：游标持久化、挂起与恢复、并发、进度、方案编辑器。Workflow 引擎已有前四项之外的所有基础设施：注册表、配置表单、类型校验、画布编辑器、运行记录、BTask 外壳、事件总线。缺的只有「运行可以停下来等一个外部信号」和「单条目的逐步游标」。因此宿主选 Workflow 引擎，并做一次范围明确、可选加入的扩展；这也直接回答了最初「要不要结合 Workflow」的问题。

方案的存放与调度。WorkflowDefinition 加 IsBuiltin：内置方案按名称播种一次，之后只读——改它的方式是复制。播种时若某方案里还有本版本尚未实现的步骤，则整份跳过、留给后续版本播种，绝不写入一份引用了不存在活动的定义。AcquisitionTask 是运行之上的索引而非第二份真相，因此需要一个运行之外的观察者：预定义任务 AcquisitionQueue（30 秒一次）把任务行与运行状态对齐，并在有空位时启动排队中的获取。两件事都只有外部才能做——方案最后一步之后没有任何东西会运行，而创建时因超限排队的任务也没有别人来启动它。并发上限只计 Running：Waiting 可能等上几天，让它占用名额只会把上限变成「最多能有几件事做到一半」。

目录名的模板。没有复用 ResourceUtils.SplitDisplayNameTemplateIntoSegments：那套机制是为「已经有属性的资源渲染显示名」写的，而放置发生在资源还没有任何属性之前，取值只能来自工作项。因此模块内是一个小得多的渲染器 AcquisitionDirectoryNamer，只借用了其中真正要紧的一条行为——取值为空的占位符连同它的括号一起消失，否则每一个没写社团名的帖子都会留下一对空方括号。

边界。只加挂起 / 恢复与单条目游标，不加分支、循环、并行分叉；不让多条目批处理挂起；方案不得自我入队（action.workflow.run 依旧不存在）。文件清洗的「先计划后确认」模式继续存在，两者互不影响。
备选宿主。若引擎扩展在实施中遇到不可接受的风险，Bakabase.Modules.Acquisition 内的独立 AcquisitionRunner（后台服务 + BTask 外壳，本方案第二版的形态）驱动同一套步骤契约，方案改存独立的 AcquisitionRecipe 表。步骤实现零改动。这是「先有抽象底层」带来的保险，也是执行计划里明确的降级路径。

7.5 关键步骤的细节

7.5.1 解析分享内容与付费内容

帖子解析器泛化为分享内容解析。输入是「任何能读出一段文本的东西」，输出是「链接 + 提取码 + 解压码 + 清洗后的标题」。现有 DownloadInfoHandler 本来就只吃 HTML 或文本，与来源无关；变化只在读取这一端。

  • 读取器按内容类型分派。网页：现有 IPostContentFetcher 改名为 ISharedContentReader，按 URL 主机选择（SoulPlus 保留现有实现；无专用读取器的主机走通用 HTML 正文抽取）。文档：新增文本、Markdown、Excel/CSV 读取器。粘贴文本：直接送入处理器。AddPostParser 的程序集扫描改为扫描所有已加载程序集。
  • 分享清单。一份文档或表格可能列出很多资源。导入时按行提取「标题 + 链接 + 密码」，每一条走 §6.2 分享渠道条目的同一套匹配逻辑；用户在预览表里逐行确认，然后可一键为全部创建获取任务。
  • 网盘种类。DownloadInfoResource 增加 DriveKind（由链接主机名规则推断，大模型输出只作参考），供 selectLink 与抓取步骤使用。
  • 付费内容改为显式挂起。SoulPlusContentFetcher 不再在抓取时购买。步骤发现付费块时：价格不超过任务生效的自动购买上限则购买并把 {价格, 时间, 帖子} 记入工作项；否则 Suspend(PaidContent)，界面显示价格与「购买并继续」。今天 null > int 为 false 导致价格未知也会买的问题一并修掉。
  • 身份。正文若含权威编号（RJ 号、Steam AppId、VNDB 链接），写入目标资源的 ResourceSourceLink；分享页面本身只作为线索与任务记录保存，永不成为身份。
  • 解析结果同时写回 PostParserTask（复用其表与页面），保持帖子解析页可独立使用。

7.5.2 等待收件箱：网盘问题的务实解法

百度、迅雷、飞猫、Cloudflare 盘要登录、验证码、官方客户端，自动化脆弱且随时失效。方案把「从网盘取回文件」留给人，其余全部自动：

  1. waitForInbox 用系统浏览器打开链接（提取码由前端复制到剪贴板），Suspend(WaitingForFile)，记录等待开始时间与期望文件名（若解析步骤拿到）。
  2. 用户以任何方式把文件放进收件箱目录（获取设置里配置一次；可以直接把浏览器/网盘客户端的下载目录设为它）。
  3. AcquisitionInboxWatcher（BackgroundService，仿 WorkflowFsWatchService）监听一层深度；「稳定」判定：无 .part / .crdownload / .tmp / .baiduyun.downloading 等后缀、连续两次采样大小不变、可独占打开；分卷组齐全后才算一个候选。
  4. 认领打分：对每个等待中的运行计算 得分 = 文件名与任务标题的归一化词元重合（ITextOps.Clean 后）+ 期望文件名精确命中 + 文件名方括号里的密码与解压码一致 + 时间接近度。唯一高分 → 以「认领信号」恢复该运行；多个接近或都低 → 该运行改为 AmbiguousInboxFile，界面并排列出未认领文件与等待中的任务，拖拽或点选完成认领。
  5. 认领后文件移到运行的工作目录（AppDataDirectory/acquisition/{taskId}/，遵守 appdata-paths.md），步骤 Continue。

这一步保留了唯一真正难自动化的动作，却消灭了密码查找、解压、搬运、配路径标记、同步。有 API 的网盘（Mega、PikPak）之后作为抓取步骤插入，把等待点自动化掉。

7.5.3 解压与密码

  • 密码候选顺序：工作项里的解压码 → 文件名方括号中的文本（StringExtensions.GetPasswordsFromPath）→ 来源站点的常用密码（配置项）→ PasswordService.Search 按最近使用取前 N（可关闭）→ 无密码。
  • 每个候选先 TestCompressedFile，成功再 ExtractWithProgress；全部失败 → Suspend(PasswordUnknown)，用户输入后以信号恢复并 PasswordService.AddUsedTimes。
  • 嵌套压缩默认再解一层；解出的单一外壳目录折叠；安装程序不解，原样放置；没有压缩包时 Skip。

7.5.4 重命名、放置与落地

  • 目录名 = 工作项的 WorkingText。默认由 place 的模板渲染（{Title}、{Code}、{Collection}、{Source}、{Year}，包装符内为空则整段丢弃）；方案里在 place 之前插入任何 transform.text.* 节点即可重命名（去掉方括号、去掉「汉化」字样、按捕获组重排）。逐段做非法字符清理与长度预算；冲突策略：追加序号 / 合并进已有目录 / Suspend(TargetExists)。默认模板 {Title}，正好匹配库根目录上 Layer = 1 的资源标记。
  • 落地始终作用于目标资源：MaterializeAsync(resourceId, targetDirectory)，不必等待同步任务；随后入队库根目录标记同步。
  • 从分享链接直接发起的任务：在创建任务之前就已按解析出的标题创建了无身份的未落地资源，并把链接挂为 AcquisitionLead；落地时若解析出更好的标题且资源名称仍是占位值则更新名称。
  • 目标目录已被另一条资源占用时，按 §4.2 的合并策略处理，以目标资源为主体。
  • 完成后：通知（Source = "acquisition:{id}"，深链接到资源）；发布 acquisition.statusChanged；若资源属于某些集合，这些集合的收集率刷新。

7.6 失败、恢复与并发

  • 步骤抛异常或返回 Fail → 运行 Failed，游标停在该步；「重试」= 从游标步骤重新入队。步骤幂等（§7.1）。
  • 进程重启：Waiting 原地保留；Running 从游标步骤重跑。
  • 并发：IAcquisitionService 控制同时处于活动步骤的运行数（默认 2，Waiting 不占名额）；每个运行就是一个 BTask（引擎已有），进度、暂停、取消经它暴露；BTaskType 加 Acquisition 便于界面筛选。
  • 取消：运行 Cancelled，工作目录清理，收件箱中已认领的文件退回收件箱。
  • AcquisitionTask 表是运行的薄索引（资源、线索、方案、运行 id、状态镜像、目标目录、购买审计），供资源卡片与获取中心按资源快速查询；状态由适配器在每次步骤结束时同步。

7.7 发起入口

所有入口最终都落到同一个调用：IAcquisitionService.CreateAsync(resourceId, lead, recipeDefinitionId?, collectionId?)。没有资源的入口先创建未落地资源；没指定方案时按线索种类取默认。

  • 资源卡片与详情：未落地资源的「获取」，选一条线索与（可选）一份方案（首要入口，不涉及集合）。
  • 资源页「新建未落地资源」对话框里勾选「创建后立即获取」。
  • 油猴脚本（src/scripts/baka-monkey）在 SoulPlus 列表页的「解析」按钮旁增加「获取到 Bakabase」：后端先解析标题创建未落地资源，再以帖子链接为线索创建任务；可选目标集合。
  • 获取中心：粘贴一个或多个链接，同上；分享清单导入。
  • 帖子解析页：已有解析结果的「转为获取任务」。
  • 集合详情页：「获取缺失条目」（对有线索的未落地成员批量创建）、单个成员的「获取」。
  • Workflow 活动 action.acquisition.create（§8），用于「订阅新增成员 → 自动获取」这类外围编排。

§12界面与配置体验

12.1 首次使用：一个向导，配一次

目标是「从 SoulPlus 用户装好软件到第一个游戏自动入库」不超过一分钟的配置。向导只有四个问题，都有默认值：

  1. 收件箱目录：默认 ~/Downloads/Bakabase 收件箱，并提示把浏览器或网盘客户端的下载目录指向它。
  2. 库根目录：游戏最终存放的地方。向导在此创建一条资源标记（ResourceMarkConfig { MatchMode = Layer, Layer = 1, FsTypeFilter = Directory }），这是用户唯一会接触到的「路径标记」，且由向导代劳。
  3. 目录模板：默认 {Title}；提供两个备选 {Collection}/{Title}、{Source}/{Title}，右侧用最近一次解析结果实时预览。
  4. 网盘偏好与自动购买上限：可跳过。

向导完成后，油猴脚本的按钮、集合页的「获取缺失条目」、资源卡片的「获取」全部可用。集合、订阅都不是前置条件。

12.2 路径标记为什么只需要配一次

当前用户担心「每个集合配一次路径标记」，根源是路径标记在今天既负责「哪里是资源」也负责「从文件夹名推属性」。本方案里流水线入库的资源，其作者、系列、来源、编号等元数据来自外部身份与解析结果，不再从文件夹名解析，因此 Property 标记对这部分内容完全不需要；Resource 标记只需库根目录上一条。存量库仍可继续使用 Property 标记，两套并存互不影响。

12.4 SoulPlus 用户的一次完整体验

  1. 在论坛列表页看到喜欢的帖子，点「获取到 Bakabase」，弹出选择集合（可不选）。
  2. Bakabase 解析帖子标题，创建一条未落地资源并挂上帖子链接作为线索，随后解析下载信息；若需付费弹出通知「需要 8 SP，是否购买」（或在上限内自动购买）。此时资源页已经能看到它，芯片显示「获取中」。
  3. 解析完成，自动打开网盘链接，提取码已在剪贴板；用户在网盘页面点下载。
  4. 文件落到收件箱，Bakabase 自动认领、用帖子里的解压码解压、放到 库根目录/作品名/、同步、写入来源身份，通知「已入库」。
  5. 资源卡片出现在库里，带来源封面与名称；若来自集合，收集率 +1。

用户手动做的事只剩第 1 步的点击、第 2 步的可选确认、第 3 步的网盘下载。

§13分期交付

每一期完成后都独立可用、可验收；顺序按依赖与收益排。前两期刻意不碰集合：先让未落地资源独立成立，再让它能被自动补齐，这两期就已消掉所有者当前最痛的人工劳动。每一期到批次、到文件级的拆解见配套的执行计划。

进度。第一期到第四期已实现并有测试覆盖；第二期的分享清单导入与平台取回也已完成。第五期只完成了平台对接器契约与三个实现（连同三个持有型订阅），其余各项与三张外部目录表的收编未做，理由见 §16 的偏离记录。进度只在本段更新。

§16关键决策记录

决策备选理由
未拥有的作品建模为 Path 为空的 Resource独立的 Work / CatalogItem 实体代码里已存在且在用；集合、搜索、卡片、属性、增强器全部免费复用；落地只是赋值。代价是一份有限的门控清单
未落地资源先于集合、独立于集合成立把未落地资源作为集合成员的附属概念漫画、动画、游戏各有来源，用户可能只想表达「缺了哪个资源」而无意建集合；独立成立后集合与订阅都只是它的聚合与批量来源
平台持有与分享获取是两种独立机制；分享渠道永不成为资源身份把论坛帖子也当作一种 ResourceSource资源不属于分享渠道，同一文件可被任意多处分享；把帖子当身份会造成一作多身份、换渠道即换身份。身份只来自持有平台与元数据权威，分享只产生线索
平台持有型集成正式化为 IPlatformConnector 契约把三张外部目录表直接改成订阅「枚举持有 + 取回 + 本地检测」是一个独立的能力集合，订阅只是其中枚举这一项的调度方式；对接器同时服务于获取流水线的平台取回路线
获取任务以资源为目标（ResourceId 必填），方式由线索决定获取任务以集合或来源页面为目标，落地后再建资源一个调用覆盖所有入口；不再有「等同步扫出资源再认领」的分支；新增来源或媒体类型只是新增一种线索的处理器
集合成员是资源，规则命中不落表全部落表 / 全部计算手动与来源成员需要「忽略」「顺序」「上次出现」这类成员级状态；规则成员没有这些状态且会随资源变化，落表只会过期
不做树形集合父子集合系列层级已由 Multilevel 属性承担；组合维度由规则承担；树形带来的边界问题收益不成比例
订阅演进为集合来源，每个订阅属于一个集合保留独立订阅，另建集合来源抓取逻辑完全相同；两个概念只会让用户困惑；停用快照后差异计算更可靠（持久化的已见集合）
获取流程先定义与宿主无关的步骤契约，再选宿主直接写死五个阶段的状态机流程是动态的：不是都来自论坛、不是都经网盘、不一定解压、可能要重命名。步骤 + 方案把「流程」变成数据，具体流程只是内置的几份方案
宿主选 Workflow 引擎，做一次最小、可选加入的扩展（挂起 / 恢复 + 单条目游标）；独立运行器为备选①独立状态机引擎（本方案第一、二版的决定）；②大改 Workflow 支持分支与批处理挂起方案编辑器、注册表、配置表单、运行记录、BTask 外壳、事件总线全部免费获得，现有文本与通知节点可直接混入方案；缺的只是「停下来等信号」。①要重复一套注册表与编辑器；②改动面失控。第一、二版反对改引擎的理由是「不想让引擎理解长流程」，现在的扩展不让引擎理解任何内容，只加一种结果与一个游标，边界见 §7.2
网盘先走「收件箱认领」，API 网盘后期插入先做网盘自动化自动化脆弱且平台众多；收件箱与站点无关，一次实现覆盖全部网盘，且为后期自动化留好了接口
付费购买改为显式停车点沿用抓取时自动购买花钱的动作必须可见、可审计、可设上限
规则集合复用 ResourceProfile 的搜索评估，不复用 SavedSearch新建第三套查询定义已有两套是历史包袱，不能再加；SavedSearch 是可变标签页状态，不适合做定义
「已落地」是独立的内部布尔属性并入 ResourceStatus两者正交：来源是否仍列出 vs 本地是否有文件
三张外部目录表在第五期收编第一期就统一它们今天能用；先在 SoulPlus 场景验证新机制，再回头迁移 DLsite 的下载与启动逻辑，降低第一期风险
