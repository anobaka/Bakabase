集合与获取流水线设计

范围：从「我想要这个作品」到「它成为库里一个带完整元数据的资源」的整条链路，以及跨来源的集合、收集率与订阅补全。首个落地场景是从论坛人工下载的 galgame 与小型单机游戏，但每一层都按漫画、同人本、同人音声、电影、电视剧同样适用来设计。

全文的现状结论均已在代码中逐条核实，引用格式为 仓库相对路径:行号（行号随代码演进可能漂移，以文件与成员名为准）。术语一律使用代码中的实际标识符，不使用自造缩写。标签含义：现有 代码里已经存在；需修正 存在但要改；新增 本方案引入；后期 明确排到后面的阶段；待定 需要实际数据或产品决定。

一句话结论

「我还没有的作品」就是尚未落地的资源：一条 Resource，Path 为空，身份由 ResourceSourceLink 的 (Source, SourceKey) 给出。代码里这种资源今天已经存在（未安装的 Steam 游戏、未下载的 DLsite 作品），本方案只是把它从三个站点的私有实现推广为通用机制。

四层拆分，自下而上

未落地资源是地基：不依赖任何集合就能创建、查看、获取、关联，「我缺了哪个资源」在这一层就能表达。获取流水线以一个未落地资源为目标，按它自带的获取线索（帖子链接、直链、某个外部身份）选择路线，把它变成已落地资源。集合是资源（含未落地资源）的命名分组，收集率 = 已落地成员 ÷ 全部成员。订阅是集合的外部真相源，负责告诉集合「应该有哪些条目」。

先做什么

第一阶段把未落地资源做成独立可用的概念：手动创建、按「未落地」筛选、关联本地目录、卡片与详情的状态表现。第二阶段做「收件箱版」获取流水线：帖子解析 → 打开链接 → 用户把文件丢进收件箱 → 自动认领、解压、按模板放置、落地。两期都不需要集合，却直接消灭当前人工流程里五步中的四步。

§4尚未落地的资源

§5集合

5.1 定义与三种成员来路

集合是一个命名的资源分组。成员资格来自三条路，可以同时存在于一个集合里：

三条来路的并集就是成员。同一资源被两条来路同时命中时只算一个成员。

5.2 收集率

收集率 = 已落地且未忽略的成员数 ÷ 未忽略的成员数。「忽略」是成员级标记（CollectionResourceMapping.IsIgnored），表示「我知道它存在但不打算收」，只对落表的成员可设。

一个值得说清楚的推论：收集率只在集合里存在未落地成员时才有信息量。纯手动加入已有资源的集合恒为 100%；纯规则集合通常也接近 100%，除非规则命中了其他订阅带进来的未落地资源。所以「有收集率」这个能力实质上等于「有外部真相源」，也就是订阅（§6）。集合页在收集率旁边给出成员构成（已落地 / 未落地 / 获取中 / 已忽略）比一个百分比更有用。

5.3 逐条回答：层级、管理、能力、关联、搜索

要不要多层级

不做树形集合实体。系列内部的层级（物语系列 / 伤物语）用 Multilevel 属性表达，这是 09-collections 已收敛的决定；「作者 + 系列」这类组合用规则表达。集合页提供「按某个属性分组显示成员」（例如按系列属性分组），视觉上得到层级，数据上不引入父子集合。理由：树形集合带来排序继承、循环、跨树移动等一整套边界问题，而两种既有机制已覆盖需求。

如何管理

集合页（列表）+ 集合详情页（成员 / 来源 / 规则 / 设置四个标签）。成员支持：排序（手动顺序，用于系列顺序）、忽略、移出、批量获取、按状态筛选。集合本身支持：颜色、封面（取成员封面拼图或手动指定）、描述、自动获取开关、获取设置覆盖。

有什么能力

  • 显示收集率与成员构成
  • 一键「获取缺失条目」（§7）
  • 订阅检查 → 通知 + Workflow 事件（§6）
  • 「在资源页打开」：把集合转成资源筛选（CollectionMulti In [id]）
  • 从 Multilevel 节点、从外部编号、从现有筛选一键创建
  • 成员为未落地资源时，其外部身份的元数据可通过增强器补属性（DLsite / Bangumi 增强器已能按名称或编号工作，见 §4.3 的关键词回退）

如何关联资源

落表成员用 CollectionResourceMapping (CollectionId, ResourceId)，与媒体库的 MediaLibraryResourceMappingDbModel 同构。规则成员不落表。一个资源属于多个集合天然成立。资源详情有「所属集合」块（克隆 DetailModal/MediaLibraryMappings）。

如何搜索

新增内部属性 ResourceProperty.CollectionMulti = 29（MultipleChoice，选项 = 集合列表），完全照抄 MediaLibraryV2Multi 的接入方式（§5.5）。索引里每个集合 id 一个键；规则成员在索引构建/资源变更时一并计算写入，因此搜索「在集合 X 里」对三种来路一致。

与 ResourceProfile / SavedSearch 的关系

规则集合的 RuleSearchJson 与 ResourceProfileDbModel.SearchJson 同一模型，评估复用 IResourceProfileService.GetMatchingResourceIdsBySearchJson，编辑器复用 ResourceFilterController。不复用 SavedSearch（它是可变的标签页状态）。ResourceProfile 继续只承载配置，不承载浏览。

5.4 自动把识别到的资源放进集合

「识别」在这里有三种确定性递减的方式，方案按顺序采用：

  1. 获取流水线自带身份。从订阅条目发起的获取任务知道自己对应哪个未落地资源，落地后成员资格不变，无需识别。这是最常见的路径，也是把身份匹配问题绕开的关键。
  2. 按外部编号匹配。存量库里的 ResourceSourceLink 今天由来源同步（ResourceSyncService.ResolveResourceForEntry / EnsureSourceLink）与解析器的迁移候选写入；增强器（含 DLsite、ExHentai、Bangumi）都不写链接，也没有 Steam 增强器。方案给关键词增强器在命中后增加写入链接的逻辑（DLsite 命中 RJ 号、Bangumi 命中条目 id 时 EnsureLinks），订阅检查时按 (Source, SourceKey) 找到已有资源就直接加入集合，不新建未落地资源。目录扫描也走同一逻辑（DLsiteWorkService.ScanFolder 的 RJ 号正则提升为共享的 TryExtractSourceKey）。
  3. 按标题模糊匹配。后期 用 ITextOps.Clean + IAliasService 归一化后比对，命中进「待确认」列表，用户确认后合并。沿用 docs/local-file-organization/modules/04-resolution.md 的保守默认：不自动合并。

§6订阅：集合的外部来源

6.1 为什么订阅就是集合来源

现有 AbstractListIdDiffProvider.FetchCurrentItemsAsync 做的事——抓一份外部列表、按条目 id 求差——和「集合应该包含哪些条目」的采集是同一个操作。区别只有两点：订阅把结果存成一份滚动快照，集合需要把每一项持久化成资源并记住它属于哪个集合；订阅的差异是对上一份快照的，集合的差异是对已持久化成员的。把快照换成资源，订阅就成为集合来源，不需要第二套抓取框架。

决定：每个订阅属于一个集合。现有三个订阅在升级时由运行时一次性迁移器为各自创建同名集合；SubscriptionSnapshotDbModel 表停用（差异改为对成员表计算）。/subscription 页面保留为「所有订阅」的总览，编辑入口迁到集合详情的「来源」标签。

§7获取流水线

获取任务把「一个未落地资源」变成「已落地资源」。它是一个状态机而不是线性流，因为中间有人工检查点（选链接、付费、认领文件、补密码）和小时级等待（网盘下载）。Workflow 引擎不能暂停也不能等待长任务，所以流水线由 Bakabase.Modules.Acquisition 自己承载，Workflow 只在边缘触发与定制（§8）。

7.2 链接解析与付费内容

  • DownloadInfoHandler 的提示词已列出 baidu / pikpak / gofile / mega / 115 / magnet，但结果里只有字符串。方案给 DownloadInfoResource 增加 DriveKind（由链接主机名规则推断，大模型输出只作参考），供 Fetching 阶段选处理器。
  • 付费内容改为显式停车点。SoulPlusContentFetcher 不再在抓取时购买。解析阶段发现付费块时：若集合（或全局）设置了「自动购买上限」且价格不超过上限，购买并把 {价格, 时间, 帖子} 记入任务的阶段数据；否则进入 NeedsAttention(PaidContent)，界面显示价格与「购买并继续」。今天 null > int 为 false 导致价格未知也会买的问题一并修掉。
  • 多个链接时默认按网盘偏好顺序（用户可配，例如 Mega > PikPak > 百度）自动选第一条；没有可用处理器的链接进入 ManualFetcher；一个都没有 → NeedsAttention(NoLinks)。
  • 解析结果同时写回 PostParserTask（复用其表与页面），保持帖子解析页可独立使用；AddPostParser 的程序集扫描改为扫描所有已加载程序集，新论坛抓取器可以放在模块里。

7.3 收件箱认领：网盘问题的务实解法

百度、迅雷、飞猫、Cloudflare 盘要登录、验证码、官方客户端，自动化脆弱且随时失效。方案把「从网盘取回文件」留给人，其余全部自动：

  1. ManualFetcher 用系统浏览器打开链接，把提取码放进剪贴板（桌面端），任务进入 WaitingForFile，记录等待开始时间与期望文件名（若解析阶段拿到）。
  2. 用户以任何方式把文件放进收件箱目录（获取设置里配置一次；可以直接把浏览器/网盘客户端的下载目录设为它）。
  3. AcquisitionInboxWatcher（BackgroundService，仿 WorkflowFsWatchService）监听一层深度；「稳定」的判定比现有静默期更严：无 .part / .crdownload / .tmp / .baiduyun.downloading 等后缀、连续两次采样大小不变、文件可独占打开。
  4. 认领打分：对每个 WaitingForFile 的任务计算 得分 = 文件名与任务标题的归一化词元重合（ITextOps.Clean 后）+ 期望文件名精确命中 + 文件名方括号里的密码与任务解压码一致 + 时间接近度。唯一高分 → 自动认领；多个接近或都低 → NeedsAttention(AmbiguousInboxFile)，界面并排列出未认领文件与等待中的任务，拖拽或点选完成认领。
  5. 认领后文件移到任务的工作目录（AppDataDirectory/acquisition/{taskId}/，遵守 appdata-paths.md），进入 Unpacking。分卷压缩包等到整组齐全再认领（用 DetectCompressedFileGroups 判断完整性）。

这一步保留了唯一真正难自动化的动作，却消灭了密码查找、解压、搬运、配路径标记、同步。它与来源站点无关，因此「复制到其他场景」的成本就是一个 IPostContentFetcher。有 API 的网盘（Mega、PikPak）之后作为 IAcquisitionFetcher 插入，把停车点自动化掉，用户不需要改任何配置。

7.4 解压与密码

  • 密码候选顺序：任务的 ArchivePassword → 文件名方括号中的文本（StringExtensions.GetPasswordsFromPath）→ 来源站点的常用密码（例如论坛固定密码，配置项）→ PasswordService.Search 按最近使用取前 N（可关闭）→ 无密码。
  • 每个候选先 TestCompressedFile，成功再 ExtractWithProgress；进度通过任务的 BTask 外壳推送到界面。全部失败 → NeedsAttention(PasswordUnknown)，界面提供输入框，输入后重试本阶段并 PasswordService.AddUsedTimes。
  • 嵌套压缩（解出来又是压缩包）默认再解一层；解出的单一外壳目录折叠。安装程序（setup.exe）不解，原样放置。

7.5 放置、同步与链接

  • 目标目录 = 库根目录 / 模板渲染结果。模板用显示名模板语法（{Title}、{Code}、{Collection}、{Source}、{Year}，包装符内为空则整段丢弃），逐段做非法字符清理与长度预算；冲突策略：追加序号 / 合并进已有目录 / 停车询问。默认模板 {Title}，即每个作品一个目录，正好匹配库根目录上 Layer = 1 的资源标记。
  • 落地始终作用于目标资源：MaterializeAsync(resourceId, targetDirectory)，不必等待同步任务；随后入队库根目录标记同步，让 Property / MediaLibrary 标记补属性。因为每个任务都有目标资源，不存在「等同步扫出新资源再认领」的分支。
  • 从帖子链接直接发起的任务：在创建任务之前就已按解析出的标题创建了未落地资源，并把 (ResourceSource.SoulPlus, 帖子 id) 作为外部身份挂上；落地时若解析出更好的标题且资源名称仍是占位值，则更新名称。
  • 目标目录已被另一条资源占用（路径标记先扫到）时，按 §4.2 的合并策略处理，以目标资源为主体。
  • 完成后：通知（Source = "acquisition:{id}"，深链接到资源）；发布 acquisition.statusChanged；若资源属于某些集合，这些集合的收集率刷新。

7.6 失败、重试与并发

  • 任一阶段异常 → Failed，记录阶段、消息、尝试次数；「重试」只重跑该阶段。处理器必须幂等：Fetching 检查工作目录已有完整文件即跳过，Placing 检查目标目录已存在且内容一致即跳过。
  • 进程重启：Fetching / Unpacking / Placing / Syncing 中的任务回到该阶段的起点重跑；WaitingForFile 原地不动。
  • 并发：同一时间最多 N 个任务处于活动阶段（默认 2），WaitingForFile 不占名额；每个活动任务有一个 BTask 外壳 Acquisition:{id}（仿 DownloaderManager 的 DownloadTask:{id}），提供进度、暂停、取消。
  • 取消：Cancelled 为终态，工作目录清理，收件箱中已认领的文件退回收件箱。

§12界面与配置体验

12.1 首次使用：一个向导，配一次

目标是「从 SoulPlus 用户装好软件到第一个游戏自动入库」不超过一分钟的配置。向导只有四个问题，都有默认值：

  1. 收件箱目录：默认 ~/Downloads/Bakabase 收件箱，并提示把浏览器或网盘客户端的下载目录指向它。
  2. 库根目录：游戏最终存放的地方。向导在此创建一条资源标记（ResourceMarkConfig { MatchMode = Layer, Layer = 1, FsTypeFilter = Directory }），这是用户唯一会接触到的「路径标记」，且由向导代劳。
  3. 目录模板：默认 {Title}；提供两个备选 {Collection}/{Title}、{Source}/{Title}，右侧用最近一次解析结果实时预览。
  4. 网盘偏好与自动购买上限：可跳过。

向导完成后，油猴脚本的按钮、集合页的「获取缺失条目」、资源卡片的「获取」全部可用。集合、订阅都不是前置条件。

12.2 路径标记为什么只需要配一次

当前用户担心「每个集合配一次路径标记」，根源是路径标记在今天既负责「哪里是资源」也负责「从文件夹名推属性」。本方案里流水线入库的资源，其作者、系列、来源、编号等元数据来自外部身份与解析结果，不再从文件夹名解析，因此 Property 标记对这部分内容完全不需要；Resource 标记只需库根目录上一条。存量库仍可继续使用 Property 标记，两套并存互不影响。

12.4 SoulPlus 用户的一次完整体验

  1. 在论坛列表页看到喜欢的帖子，点「获取到 Bakabase」，弹出选择集合（可不选）。
  2. Bakabase 解析帖子标题，创建一条未落地资源并挂上帖子链接作为线索，随后解析下载信息；若需付费弹出通知「需要 8 SP，是否购买」（或在上限内自动购买）。此时资源页已经能看到它，芯片显示「获取中」。
  3. 解析完成，自动打开网盘链接，提取码已在剪贴板；用户在网盘页面点下载。
  4. 文件落到收件箱，Bakabase 自动认领、用帖子里的解压码解压、放到 库根目录/作品名/、同步、写入来源身份，通知「已入库」。
  5. 资源卡片出现在库里，带来源封面与名称；若来自集合，收集率 +1。

用户手动做的事只剩第 1 步的点击、第 2 步的可选确认、第 3 步的网盘下载。

12.5 路径标记配置体验的改进（面向存量库）

  • 预设：把帮助中心 topics/pathMark/examples.ts 里的十二个示例提升为可一键应用的预设（每个预设 = 有序的 {type, configJson, priority} 列表，即 copyMarks 的 CandidateGroup.marks（完整 PathMark 对象数组）去掉 id / path / syncStatus 等实例字段后的子集），入口在 AddMarkDropdown 与树形视图右键。
  • 按样例标记：右键一个「确定是资源」的目录 → 系统按它相对根目录的深度推断 Layer，用现有 previewPathMarkMatchedPaths 展示将命中的兄弟目录，用 MarkDescription 人话描述，确认后批量创建（POST path-mark/batch）。
  • 复制标记持久化：copyMarks 目前是会话级状态，提升为可命名保存的预设，服务端存储。
  • 职责说明：帮助中心明确「资源标记回答哪里是资源；属性来自外部来源或属性标记；配置集中在 ResourceProfile」，减少用户对三种标记的困惑。

§16关键决策记录

决策备选理由
未拥有的作品建模为 Path 为空的 Resource独立的 Work / CatalogItem 实体代码里已存在且在用；集合、搜索、卡片、属性、增强器全部免费复用；落地只是赋值。代价是一份有限的门控清单
未落地资源先于集合、独立于集合成立把未落地资源作为集合成员的附属概念漫画、动画、游戏各有来源，用户可能只想表达「缺了哪个资源」而无意建集合；独立成立后集合与订阅都只是它的聚合与批量来源
获取任务以资源为目标（ResourceId 必填），方式由线索决定获取任务以集合或来源页面为目标，落地后再建资源一个调用覆盖所有入口；不再有「等同步扫出资源再认领」的分支；新增来源或媒体类型只是新增一种线索的处理器
集合成员是资源，规则命中不落表全部落表 / 全部计算手动与来源成员需要「忽略」「顺序」「上次出现」这类成员级状态；规则成员没有这些状态且会随资源变化，落表只会过期
不做树形集合父子集合系列层级已由 Multilevel 属性承担；组合维度由规则承担；树形带来的边界问题收益不成比例
订阅演进为集合来源，每个订阅属于一个集合保留独立订阅，另建集合来源抓取逻辑完全相同；两个概念只会让用户困惑；停用快照后差异计算更可靠（持久化的已见集合）
获取流水线是独立状态机，Workflow 只做触发与粘合扩展 Workflow 引擎支持暂停/等待与 08-orchestration 已论证的三处结构性错配一致；引擎保持线性与短命才能维持「引擎零改动加节点」的优势
网盘先走「收件箱认领」，API 网盘后期插入先做网盘自动化自动化脆弱且平台众多；收件箱与站点无关，一次实现覆盖全部网盘，且为后期自动化留好了接口
付费购买改为显式停车点沿用抓取时自动购买花钱的动作必须可见、可审计、可设上限
规则集合复用 ResourceProfile 的搜索评估，不复用 SavedSearch新建第三套查询定义已有两套是历史包袱，不能再加；SavedSearch 是可变标签页状态，不适合做定义
「已落地」是独立的内部布尔属性并入 ResourceStatus两者正交：来源是否仍列出 vs 本地是否有文件
