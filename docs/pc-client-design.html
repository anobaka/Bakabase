§1名词约定

本文出现的每个名词都在这里给出完整定义，正文中不使用缩写。

名词含义
一体版今天发布的桌面应用。同一个进程里既有界面外壳，也有数据库、媒体库和后台任务。用户的电脑既是客户端也是服务端。英文对应 all-in-one。
服务端部署只运行 Bakabase.Service，没有图形界面。今天的 Docker 镜像就是这种形态。数据库和媒体库都在这台机器上。
纯客户端本设计要新增的形态。桌面应用连接一台远程的服务端部署，自身不持有数据库和媒体库。目标是让用户感觉与一体版没有区别。
数据侧存放数据库与媒体库的那一侧。一体版里是用户的电脑，服务端部署里是服务器。
用户侧用户此刻正坐在前面的那台机器。一体版里与数据侧是同一台，纯客户端里是两台不同的机器。
本地转发层纯客户端模式下，桌面应用同一个进程内再起的一个 Kestrel 宿主，只绑定回环地址。它把大部分请求转发给远程服务端，同时自己执行必须在用户侧发生的那部分请求。不是独立进程——初稿写的"小型 HTTP 进程"是错的。详见 §4。
远程访问闸门现有的两层机制：RemoteAccessMiddleware（判断这个连接是否被允许）与 RemoteAccessAuthorizationFilter（判断这个端点是否允许被远程调用）。

§3关键发现：完整功能的远程访问今天已经存在

把 BakabaseStartup.cs:111 和 RemoteAccessAuthorizationFilter.cs:30 这两条放在一起看，会得到一个对本设计影响极大的结论：

今天用 Docker 部署一台 Bakabase，用浏览器打开它的地址，得到的已经是一个功能完整的客户端。 因为 Docker 默认 Unrestricted，而该模式下端点授权过滤器整体跳过，512 个端点全部可以远程调用；单页应用本身也由同一个服务端提供，所以版本天然一致。

这意味着"纯客户端"要新增的东西，比直觉上以为的少得多。它相对于"用浏览器打开服务器地址"的增量价值只有两条：

  1. 原生外壳：独立窗口、托盘、单实例、自动更新、启动即进入应用而不是先开浏览器。
  2. 把应该在用户面前发生的命令，真的在用户面前执行：用本机的播放器打开影片、用本机的文件管理器打开目录、用本机的浏览器打开链接。这些今天在远程浏览器里要么被拒绝，要么会跑到服务器上去执行。

第二条正是提问里点到的"本地命令怎么处理"。所以整个设计可以收敛成一个很干净的题目：如何把端点按执行位置一分为二，并解决由此带来的路径语义问题。

§4架构选型：三个候选与结论

候选一：纯外壳，直接加载远程单页应用

桌面外壳不启动任何本地服务，内嵌浏览器直接指向 http://服务器地址:端口。

  • 优点：功能对等免费获得，单页应用由服务端提供，版本天然对齐。
  • 缺点：所有用户侧能力都没有了。要恢复，必须新造一套网页与原生外壳之间的调用通道，并且前端要为这套通道单独写一份调用分支。前端改动面大，而且这些分支会同时存在于一体版的代码里。

候选二：本地转发层（推荐）

桌面外壳在同一个进程内再起一个 Kestrel 宿主，只绑定回环地址的一个固定端口。内嵌浏览器指向它。它做两件事：

  1. 转发：把数据侧的请求原样转发给远程服务端，包括实时推送连接。对网页来说仍然是同一个来源，不涉及跨来源资源共享问题。
  2. 本地执行：把用户侧的请求留在本进程执行，也就是在用户自己的机器上拉起播放器、打开目录。
这个方案最大的好处：现有前端几乎不用改。 BApi.tool.openFileOrDirectory 打开的自然就是客户端的文件管理器，/player/batch-play 拉起的自然就是客户端的播放器——因为这些请求根本没有被转发出去。前端不需要知道自己身处哪种模式。

单页应用本身仍然从远程服务端拉取，不由本地转发层内置。这样可以避免"新客户端连旧服务端"时前端调用了服务端还不存在的接口。版本兼容由已有的协议版本握手负责。

候选三：前端维护两个接口地址

前端持有两个接口客户端，逐个调用点判断该发往本地还是远程。最灵活，但侵入面最大：每个调用点都要判断，跨来源资源共享与实时推送连接都要单独处理，而且这些判断会永久留在一体版的代码路径里。不推荐。

结论：采用候选二

安全边界：本地转发层必须只绑定回环地址，并且校验 Host 头。 如果它监听了所有网卡，局域网里任何人都可以让这台客户端打开目录、拉起播放器、读取已映射的本地文件。它也不参与服务发现广播，不响应探测请求——它不是服务端。

只绑回环还不够：任意网页都能向 127.0.0.1 发请求，而转发层会用设备密钥替这些请求签名。所以还要三条——Host 头不是预期的 127.0.0.1:{端口} 就返回 400（挡住 DNS 重绑定）；非 GET 请求校验 Origin；内嵌浏览器使用按风味隔离的用户数据目录，免得一体版与客户端共用同一份会话与登录态。

4.4 实时推送连接的转发：实现时必须验证的清单

界面的实时数据推送（/hub/ui）要穿过本地转发层。这不需要任何人做决策，但实现阶段必须逐条验证下面这些点，因为它们是转发长连接时最常见的失败方式：

验证项失败时的表现
协商请求的响应被正确透传连接建立失败。协商响应里带有连接标识，若被转发层改写或丢弃，后续请求就对不上
连接升级（WebSocket）整体透传，/hub/ 前缀下的全部路径推送不可用或退化为长轮询
连接升级（WebSocket）被透传，而不是被当成普通请求缓冲降级到长轮询，界面更新延迟明显变大
心跳与保活帧双向透传，且转发层不设置比服务端更短的空闲超时连接每隔一段时间被静默掐断，界面数据停止更新且没有报错
服务端重启后，客户端能自动重连需要用户手动重启客户端才能恢复
响应不被压缩或缓冲推送数据积压在转发层，界面成批跳变而不是连续更新
第二条实时通道 /hub/progressor 同样要透传初稿只点了 /hub/ui。进度类推送失效而界面不报错
服务端推送事件流 /resource/discovery/stream 不缓冲资源发现结果整批延迟到达或不到达
范围请求与 HEAD 透传，客户端断开时取消上游播放器无法跳转；断开后服务端的转码槽位泄漏

4.5 客户端与服务端版本不匹配 所有者已确定：宽松降级

先看清楚什么东西可能不匹配——因为单页应用是从远端拉的（§4 候选二），界面与服务端永远是配套的，不存在版本差。这也意味着客户端安装包不携带网页前端，连接之前的界面是外壳里的原生视图。真正可能落后或超前的只有外壳这一侧：本地转发层，以及它编译进去的那份用户侧端点清单。

不匹配的内容后果策略
服务端新增了一个用户侧端点，旧外壳不认识外壳把它转发出去，服务端因为自己也标了这个端点而拒绝降级。两侧都设防，失败是明确的，不会跑到服务器上执行。界面提示"该功能需要更新客户端"
服务端新增了普通功能端点界面来自服务端，所以功能是完整的；外壳只负责转发，不需要认识它无影响，不必提示
外壳比服务端新，调用了服务端没有的端点404降级，提示"该功能需要更新服务端"
配对与签名的握手方式变了连不上硬失败。这一层没有降级空间，必须明确报出"需要升级哪一端"
结论：功能层面一律宽松降级，只有认证握手本身硬失败。 界面上需要一个持续可见的提示（不是一闪而过的提示条），说明当前客户端与服务端版本不一致、以及建议升级哪一端。已有的协议版本握手（RemoteAccessProtocol.CurrentVersion）继续用来判断"是否属于硬失败"，而不是用来一刀切地拒绝连接。

5.1 用同一个安装包，还是发两个安装包

本节结论已被决策 06 推翻，改为发两个安装包。下面的表保留原样，因为它列的对比项仍然成立——变的是权重。初稿把"现有用户升级后毫无感知"当成决定性理由，但那条在两种做法下都能满足：一体版安装包本身不变，客户端是另一个产物，现有用户根本不会遇到它。

真正翻盘的是另外三点，详见执行计划 §5.1：一，"运行时切换模式"要求在选定数据目录之前覆盖静态锚点，而那个入口挂在 AppService 上就一定失效（它的静态构造函数会先跑）；二，同机双跑要求单实例标识不同，同一产物两种模式做这件事是额外的运行时分支，两个产物则天然不同；三，构建期分离之后"客户端不碰数据库"是链接期保证，而不是要靠纪律维持的约定。

代价也记在这里：构建矩阵从 4 条腿变成 7 条，客户端需要自己的包标识与更新通道，用户在下载页要做一次选择。体积收益实测只有 25%（191 MB → 约 142 MB，linux-x64 自包含未裁剪），不是理由。

推荐同一个安装包、同一个可执行文件，运行模式是应用内的一个设置项，默认值是一体版。

对比项同一个安装包两个安装包

误操作风险用户可能误切模式。缓解：切换需显式确认并说明后果，且可随时切回，本地数据不受影响无此风险

5.2 进程组合方式

风味在构建期决定（决策 06）：新增一个与 RuntimeMode 并列的构建属性 -p:AppFlavor=AllInOne|Client，两个风味各有自己的入口工程——src/apps/Bakabase（引用 Bakabase.Service）与 src/apps/Bakabase.Client.App（引用 Bakabase.Client），共用抽出来的 Bakabase.Shell。

不要往 RuntimeMode 里加取值：它现在的含义是"我是哪个平台的服务端宿主"（Dev / WinForms / Docker / MacOS），每个消费方都假设自己是服务端，而客户端在 Windows 与 macOS 上仍要区分平台，塞进去会变成 CLIENT_WINFORMS 这种正交概念相乘。另外更正初稿的两处事实：该枚举位于 LazyMortal 子模块，两个子模块都已签出，"本仓库未签出"不成立。

真正重要的是组合根的位置：

两个风味各自使用独立的组合根类。 一体版继续使用今天的 BakabaseHost 与 BakabaseStartup，这两个文件一行都不改；纯客户端使用新增的独立组合根，只注册转发、用户侧执行、路径映射三类服务，不注册数据库上下文、不执行数据库迁移、不注册后台任务、不注册增强器与下载器。

这样做的代价是新增一个组合根类；换来的是"一体版的服务注册代码没有被修改过"这个可以用差异比对直接验证的事实。如果改成在 BakabaseStartup 里加条件分支，就再也无法给出这个保证。

构建期分离把这条保证又推进了一层。一体版入口根本不引用 Bakabase.Client，两者不在同一张引用图上。控制器发现、选项描述器扫描、后台任务构建器扫描这三类扫描的范围都是"入口程序集及其引用程序集"，所以客户端的类型不可能被一体版扫到——这从"必须遵守的纪律"变成了"编译期事实"，断言可以直接下在程序集层面而不是容器描述符层面。

外壳共享库 Bakabase.Shell 对宿主只依赖一个三成员的接口 IShellHost（IHost、Start、Dispose），由入口工程提供实现，因此它自己也不引用 Bakabase.Service。此项已实现：搬移前后发布产物 571 → 573 个文件，差异只有外壳程序集、其调试符号与随之改名的本地化资源，总体积不变。

5.3 同一台机器上同时运行服务端与客户端

所有者已确认这个组合必须允许。它带来两条具体要求：

  • 单实例标识必须按风味区分。今天 BakabaseHost.SingleInstanceId 是固定的 "Bakabase"（BakabaseHost.cs:36），它推出互斥体 Bakabase_SingleInstance_Mutex 与管道 Bakabase_SingleInstance_Pipe（AppHost.cs:63-64）；共用的话第二个进程会被单实例机制直接挡掉。纯客户端用 Bakabase.Client。本条是对的，但执行计划初稿里写成了"互斥体/管道名格式不变"，与它直接矛盾——已按本节更正。
  • 服务器列表里要能看见本机。一体版只要开启了远程访问，它本身就是一台合格的服务端——不需要单独部署什么东西。所以客户端的服务器选择界面应当把本机发现到的服务端也列出来，并明确标注"本机"，避免用户以为列错了。
  • 多台服务端之间是窗口内切换，不允许多开 所有者已确定。一台客户端可以配对多台服务端（本机的、别的设备的），但同一时刻只连一台，切换在窗口内完成，与移动端已有的做法一致。这也让单实例标识保持简单：一个模式一个标识即可，不必再按连接的服务器细分。
由此得到一条值得对外说明的拓扑：想把自己电脑上的媒体库共享给另一台电脑的用户，不需要改用服务端部署——一体版开启远程访问，另一台机器用纯客户端配对连接即可。服务端部署（Docker）针对的是"没有图形界面的常驻机器"这个不同场景。

5.4 数据目录：与一体版物理隔离

所有者已确认：纯客户端使用独立的应用数据目录，不与一体版共用。初稿写的是"约定纯客户端不触碰一体版的数据"，物理隔离比约定可靠得多，理由有四条：

  • 切回一体版后本地数据完好无损，这件事自动成立，不依赖任何代码纪律。
  • §5.3 允许同机同时运行两种模式，共用目录会直接冲突（配置文件、日志、锁文件）。
  • 客户端自己有需要持久化的东西：服务器档案与配对凭据、路径映射表、客户端自身日志、窗口状态。它们需要有自己的家。
  • §10.1 里"纯客户端不应产生数据库文件"这条验证，因为目录隔离而变成一句 assert 目录不存在，比扫描共享目录可靠。

目录位置遵循 appdata-paths.md 的全部规则（不得位于安装目录下，Windows 上必须与安装根隔离）。命名上与一体版并列而非嵌套，例如 Windows 下 %LocalAppData%\Bakabase.Client.AppData，macOS 与 Linux 用各自平台的对应位置。

怎么实现：换档案，而不是加抽象 所有者已确定

所有者的要求是：环境变量名的差异（以及"数据目录在哪"这件事本身）应当对数据目录之外的逻辑完全隐藏。这个方向是对的，但初稿描述的落地方式在代码里没有落点，必须更正。

更正：不能"在组合根里注入不同的路径解析器"。初稿说这个架构今天已经基本成立、上层一行不用改。核实之后不成立：AppService 没有接口，AppDataDirectory 与 RequestAppDataDirectory 是非虚成员并硬连到静态的 DefaultAppDataDirectory。组合根建立的时候，目录早就解析完了——依赖注入根本没有机会参与这件事。

实际做法是在解析之前换掉档案，落在子模块里，全部是加法：

  • 新增 AppDataPathProfile，把"环境变量名 + 平台默认位置"打包成一个档案。一体版档案与今天逐字相同（BAKABASE_DATA_DIR / Bakabase / Bakabase.AppData），客户端档案是另一组。
  • DefaultAppDataPathResolver.Resolve 增加一个接收档案的重载，旧签名委托过去并传一体版档案。
  • 新增静态类 AppDataAnchor（Current + Use(profile)），由 AppService 的静态构造函数读取；已解析后再调用 Use 则抛异常。客户端入口的第一条语句调用它，一体版从不调用。
这个入口绝对不能挂在 AppService 上。它有显式静态构造函数（AppService.cs:184-216），第 202 行就 Directory.CreateDirectory(DefaultAppDataDirectory)，随后跑旧版锚点迁移、创建日志文件。C# 保证静态构造函数在任何静态成员被引用之前执行——包括 AppService.UseAppDataAnchor(...) 这次调用本身。写成那样的话，一体版目录会在锚点被设置之前就建好，迁移也已经跑完。所以必须是独立类型。

调试目录天然隔离：解析器的调试分支用的是 {入口程序集名}.Debugging（DefaultAppDataPathResolver.cs:47-52）。构建期分离之后两个入口程序集名不同（Bakabase / Bakabase.Client），调试目录自动分开，档案里不需要再塞一个调试后缀。

不要用"进程内设置环境变量"取巧：/app/restart 用 Process.Start 拉起的新进程会继承环境变量。

"启动锚点不构成障碍"这句要划掉。初稿把 DefaultAppDataDirectory 的静态性质当成一个可以绕开的细节，还漏算了调用点——含子模块在内实际有 18 处，其中 4 处是运行时调用而非设计时工厂。启动锚点恰恰是唯一重要的那一处：Bakabase/Program.cs:45 是整个进程第一次触碰 AppService 静态成员的地方，客户端能不能拿到自己的目录，全看它之前有没有换掉档案。上面的 AppDataAnchor 就是为此存在。

剩下的数据库上下文工厂确实是 EF 的设计时工厂，运行时不走。但由此得到的验证项仍然有效：纯客户端必须确保自己不触发这些路径（不构造数据库上下文），否则会静默拿到一体版的目录。构建期分离之后这条更强了——客户端根本不链接 EF，触发不了。已记入 §10.1。
关于更彻底的版本，我建议不做。 把"增删改查数据目录"整个包成接口（连 File / Directory 调用也走接口）确实更彻底，但：RequestAppDataDirectory 已经提供了"要一块地方"的语义；纯客户端自己要存的东西（服务器档案、配对凭据、路径映射表、客户端日志、窗口状态）都是新写的代码，不依赖旧代码被改造；而这项重构会大面积触碰历史代码，直接冲撞本设计的第一约束。
建议作为一次独立的可选清理，用它自己的理由立项，不搭这趟车。

§6执行位置：本设计的核心概念

6.1 现有标记混淆了两件不同的事

今天的 [RemoteAccessible] 是默认拒绝的：没有标记的端点一律不允许远程调用。512 个动作里只有 52 处标记，剩下 460 个未标记的端点其实混着两类完全不同的东西：

  • 只是还没有人去审查过——绝大多数属于这类。它们完全可以远程调用，只是当初为移动端开放端点时没必要一次性审完。
  • 确实必须在某台特定机器上执行——拉起播放器、打开目录、打开浏览器。这类是少数。

做纯客户端必须把这两件事拆开。否则要么客户端功能残缺（大量端点被拒），要么为了开放而逐个标记 460 个端点（改动量巨大，且极容易误把用户侧端点标成可远程，导致命令跑到服务器上执行）。

6.2 新增标记：[RunsOnUserMachine]

新增一个与 [RemoteAccessible] 正交的标记，含义是"这个端点的效果落在运行它的那台机器上，所以它必须在用户面前的机器上执行"。它有两个用途，两侧各用一次：

使用方作用
服务端无论调用方是否已认证，一律拒绝远程调用这类端点——因为在服务器上打开一个窗口，用户根本看不见。
本地转发层据此决定哪些请求不转发，而是自己执行。

两侧各自编译进自己的那份标记，不需要在运行时同步一张路由表。版本不一致时最坏的情况是：客户端把某个端点转发了出去，而服务端因为自己也标了这个端点而明确拒绝并给出原因。两侧都设防，不会出现"命令悄悄在服务器上执行了"的情况。

关键更正：服务端的拒绝集合 ≠ 转发层的拦截集合。初稿把这两件事当成同一张表。实际上有一批端点服务端不能拒绝远程调用，但客户端必须本地处理——例如用户脚本的安装地址、远程访问上下文接口、PATCH /options/app 里按字段拆分（语言存服务端、窗口行为存客户端）、以及 /app/restart 在客户端语义下重启的是客户端自己。

所以转发层的拦截集合 = [RunsOnUserMachine] 集合 + 一份显式覆盖表。覆盖表必须是显式的、有测试锁定的，不能靠实现者临场判断。
还有一处顺序问题。端点授权过滤器第 30 行判断的是 IsUnrestricted（= IsLoopback || Mode == Unrestricted），不是回环。新的用户侧检查如果放在它之后，对 Docker 默认的 Unrestricted 模式根本不生效——而那恰恰是今天问题最大的场景：远程浏览器调 /resource/{id}/play 会在服务器上拉起播放器并返回成功。检查必须插在回环直通之后、IsUnrestricted 判断之前。

§7身份认证：解锁完整功能的前提

现有的信任模型是"能连上端口就被信任"，没有身份、没有配对、没有传输层加密，把局域网本身当作安全边界。RemoteAccessOptions 的注释把这个立场写得很清楚，并明确说了"不适合做端口转发"。

这个立场在今天成立，因为使用场景是"自己家里的手机连自己的电脑"。但本设计要做的事情，是官方鼓励用户把服务端部署到自己的服务器上。一旦鼓励这种部署，公网访问和反向代理就会成为常态，而"能连上就信任"在那个场景下不可接受。

认证是纯客户端发布前的前置条件，不是后续优化项。 但它必须以"现有默认行为完全不变"的方式引入：Disabled / Enabled / Unrestricted 三个取值的语义与各自的默认值一律不动，现有的局域网手机用户不会因此被要求配对。
这是一次有意的方向回退，实现前请先读旧实现。 提交 85e2c05（2026-08-29，drop device pairing, treat anything that can connect as trusted）删掉的正是设备配对——当时的理由是"能连上就被信任，身份层是只有成本没有收益的"。现在重新引入，是因为使用场景变了：本设计要鼓励把服务端放到用户自己的服务器上，那个前提不再成立。
被删掉的实现包含配对码、令牌存取与吊销、承载令牌的 cookie、RemoteDevice 与 RemoteDevicePlatform 模型，以及 §7.5 讲到的签名地址。

更正："可以直接取回"说得太满，实际分三类：
可以取回——设备与平台模型、配对码生成与校验、设备增删改查、签名令牌及其 9 个测试、服务端视图模型。

输入负担每台设备都要输一次密码，还容易被用户设成弱口令或复用配对一次，之后无感；凭据由程序生成，不存在弱口令
泄露面一处泄露，全部沦陷一台设备的凭据泄露，只影响那一台

7.2 第一台设备怎么配对

这是设备配对唯一真正的难点：配对通常需要在服务端做一次确认，而服务端部署没有图形界面，用户没地方点"批准"。分三种情况处理：

场景做法
服务端部署（无图形界面）的第一台设备服务端启动时，若一台设备都没配对过，就把一个配对码写进日志与标准输出。Docker 用户用 docker logs 即可看到。配对码有有效期，用掉即失效，用完再启动不再打印
一体版兼作服务端的第一台设备它有图形界面，直接在设置页里显示配对码或"批准这台设备"的按钮，不必去翻日志
后续设备由任意一台已配对的设备批准——客户端收到配对请求通知，用户点一下即可。这样用户不必再回服务端翻日志

7.3 凭据形态：不做传输层加密，就不要把长期凭据放在网线上

所有者已确认不做传输层加密。既然如此，凭据的传输方式就需要选得更谨慎一些：

更正："服务端只保存摘要"与所选算法不兼容。决策 3 定的是 HMAC-SHA256，而 HMAC 是对称的——服务端必须持有密钥原文才能验证签名，摘要验不了。想让服务端只存公钥就得改用非对称签名（ECDSA P-256），那需要在 Dart 侧额外引入依赖，成本与收益不匹配，已按决策 3 排除。
配对时客户端与服务端各自保存同一份设备密钥。服务端侧的密钥文件必须存在 devices.json 里，绝不能进入任何 [Options] 类型——所有选项对象在 /hub/ui 连接建立时会被整体推给对方（WebGuiHub.cs:108-146），放进去等于把密钥广播出去。
之后每次请求不携带这份密钥本身，而是携带一个用它对"请求方法 + 路径 + 时间戳 + 一次性随机数"计算出的签名，放在 Authorization 请求头里。服务端用自己那份密钥验证签名，并拒绝时间戳过期或随机数重复的请求。

这样做的收益很具体：即便有人在局域网上被动抓包，也拿不到那份长期凭据，因而无法在之后任意时刻冒充这台设备。代价只是多一次签名计算，不引入证书、不引入任何需要维护的加密基础设施。

两条实现约束。一，签名放在 Authorization 头意味着它不进入地址，所以不会破坏 /tool/thumbnail 那条 [ResponseCache] 的缓存键；但反过来，凡是靠地址取流、无法带请求头的消费方（外部播放器、移动端原生播放器、浏览器直接播放）都用不了它，那正是 §7.5 签名地址存在的理由。二，不支持普通浏览器配对：单页应用内为每个请求签名、以及给 WebSocket 的查询串签名，工作量大且本设计没有这个需求。局域网浏览器保持未配对行为。
必须对用户说清楚：不做传输层加密意味着内容是明文的。 签名只解决"身份不被冒用"，完全不解决"内容不被看到"。同一网络里的旁观者仍然可以看到你在浏览和播放什么，也可以把媒体流原样抓下来。因此文档必须明确：打算把服务端暴露到公网的用户，请自行在前面套一层带传输层加密的反向代理；本设计不提供这个能力，也不假装提供。

7.4 与现有远程访问模式的关系

配对机制是叠加在现有三个模式之上的，不改动它们：

  • 一体版：请求走回环地址，在闸门第一步就直通（RemoteAccessMiddleware.cs:52），永远走不到配对逻辑。
  • 未配对的局域网设备（今天的移动端）：行为完全不变，仍然只能访问标记了 [RemoteAccessible] 的端点。已有用户不会因为这次改动被要求配对。
  • 已配对的设备：除 [RunsOnUserMachine] 标记的端点外全部可用。这正是"功能与一体版一致"的实现方式，也是不必逐个去标那 460 个端点的原因。
  • 按模式逐一说清楚，别只说"零变化"：Disabled 下连已配对设备也一律拒绝——这个模式的语义是"完全不开放"，配对不是绕过它的后门；Enabled 下未配对设备维持今天的 52 个端点，配对后解锁全部；Unrestricted 下未配对本来就已经是全量，所以配对在这个模式下不增加任何能力，移动端不得在该模式下提示用户配对，否则是在推销一个没有收益的步骤。
  • Disabled / Enabled / Unrestricted 三个取值的语义与各自的默认值一律不动。
移动端也切换到设备配对 所有者已确定：能切最好，统一体验
切换后移动端也能摆脱今天只能访问 52 个端点的限制，两端的连接方式与设置界面也统一了。
但迁移方式必须保护现有用户：保留"未配对"作为一种受限状态，其行为与今天完全一致（仍是那 52 个端点）。配对是一次可选的升级，配了就解锁全部功能，不配也照常用。这样已装 App 的用户升级后不会被一个登录墙拦在外面，与本设计的第一约束一致。

7.5 外部播放器拿不到凭据：需要签名地址

更正：这个洞的适用范围比初稿说的窄。初稿说"认证一旦生效，这条播放路径会直接失效"。实际上 /file/raw 今天在 Enabled 与 Unrestricted 下本就匿名可达，配对是叠加的，不会把它变成必须认证。

签名地址真正的必需场景只有三个：一，打开了 RequirePairing（决策 4）之后，未配对请求只剩配对握手可达；二，媒体库之外的路径，会被路径守卫拦下；三，移动端与浏览器把地址交给原生播放器。

桌面纯客户端不在其中：它的本地播放器拿的是 http://127.0.0.1:{端口}/file/raw，由本机转发层代签并透传范围请求，播放器零依赖。

解决办法是签名地址：由已配对的调用方请求一个带签名参数的临时地址，签名覆盖具体文件路径并带有效期，外部播放器凭这个地址即可取流，无需任何凭据。

  • 签名限定到单个文件，不能是一张可以换任意文件的通行证。
  • 有效期取"够长到看完一部片子，够短到分享出去很快失效"，并且要能覆盖播放器中途重新发起请求的情况（跳转会产生新的范围请求）。
  • 这条路径同样适用于移动端把流交给原生播放器，以及浏览器里直接播放的场景。

同样地，85e2c05 删掉的就有这套签名地址（提交信息原话："signed URLs so a native player could satisfy an auth check"）。实现时优先取回旧代码。配对与签名地址都不升 RemoteAccessProtocol.CurrentVersion——升版本会把老客户端整体挡在外面，与"宽松降级"相悖；能力是否可用应当由 server-info 的能力字段表达。

§8路径语义与路径映射

这是提问中点到的问题，也是本设计里唯一没有现成基础设施的部分。服务端的一个路径（比如 /media/anime/xxx.mkv）在客户端机器上不存在，而本地播放器需要一个自己能打开的东西。

8.1 三层降级

优先级方式说明
第一路径映射用户配置好服务端路径前缀与本机挂载点的对应关系（例如服务端 /media/anime 对应本机 Z:\anime）。命中后本地播放器直接打开本地文件：跳转、外挂字幕、多音轨全部正常，服务器零消耗。这是最好的体验，也是网络存储用户的常态。
第二流式地址未命中映射时，交给本地播放器一个 /file/raw 地址。已支持断点范围请求，可以跳转。零配置即可用。前端已有的 playerSchemes.ts 沉淀了把流地址交给桌面播放器的完整知识，可以直接复用。
更正：桌面纯客户端不需要签名地址——本地播放器拿的是回环地址 http://127.0.0.1:{端口}/file/raw，由转发层代签并透传范围请求。签名地址只在移动端、浏览器，以及打开了 RequirePairing 的场景下才必需（§7.5）。
第三明确禁用没有流式等价物的操作（打开目录、打开回收站）在未命中映射时不可用。返回明确原因，界面提示用户去配置路径映射，而不是静默失败或报一个看不懂的错误。

8.2 映射表的形态

  • 存在客户端，不是服务端。每台客户端的挂载点都不同，放服务端是错的。存放位置遵循 appdata-paths.md 的约定。
  • 按服务器唯一标识分组。一台客户端可能连接多台服务器，服务器唯一标识已经存在（RemoteAccessOptions.ServerId），且能跨地址变化保持稳定。
  • 最长前缀匹配。一条映射是一对前缀，匹配时取最长的那条。
  • 配置引导：从服务端拉取媒体库列表，把它们的根路径列出来让用户逐个指定本机挂载点，而不是让用户凭空填。保存时校验本机路径确实存在。

8.3 容易踩的坑

坑处理
路径分隔符不同服务端是 Linux、客户端是 Windows 时需要转换。更正：初稿说 CrossPlatformPath 已有雏形——它做的是"把地址改成本操作系统的分隔符"，不是跨机器路径转换，直接扩展会走偏。真正可复用的是 RemotePathNormalizer（归一化）与 StandardizePath（标准化），映射层建在它们之上
大小写敏感性不同按客户端操作系统的规则做匹配，因为最终要在客户端打开
通用命名约定路径Windows 客户端的挂载点可能是 \\server\share 而不是盘符，两种形式都要支持
压缩包内的条目本身就没有真实路径，只能走流式地址；且流式提取不支持跳转，需要如实告知
配置了路径映射但网络存储此刻没挂上打开失败时自动降级到流式地址，并提示映射可能失效
资源画像里配置的播放器可执行文件路径它存在服务端数据库里（ResourceProfileDbModel.PlayerSettingsJson），指向的是当初配置那台机器的文件系统。同一台服务端被 Windows 与 macOS 客户端共用时必有一方失效。按决策 7：客户端用 KnownPlayerDefinitions.MatchByExecutable 识别服务端配置的是哪一款播放器，再用本机发现结果替换路径；识别不出就退到系统默认播放器。不改数据模型

8.4 写文件类功能的落点

文件处理器、批量修改、下载器、资源移动这些会写文件的功能，落点必须是服务端。这在语义上是对的——数据在服务端——但界面上需要让用户明白"我现在配置的是服务器上的路径"。文件浏览器组件本来就在列举服务端目录（§2），所以行为已经正确，需要补的只是文案。

§9需要跨机器协作的三个特例

9.1 登录态采集窗口

这是本设计里最麻烦的一处，所有者也点到了：凭据是在客户端的浏览器环境里拿到的，服务端未必能用。先把今天的机制说清楚，才能看出纯客户端下具体坏在哪一环。

今天是怎么做的

现有实现比"抓一个 cookie"要讲究得多，环境一致性已经是它的设计目标：

  • CookieCaptureOrchestrator 通过 IGuiAdapter.CreateWebViewSession 在本进程弹出登录窗口，采集 cookie。
  • 采集端点连同 cookie 一起返回 User-Agent 与推断出的 TLS 指纹预设（ToolController.cs:76-84），后续第三方请求会用这套配置发出（AbstractThirdPartyHttpMessageHandler.cs:121-125、TlsPresetHelper）。
  • 还存在一条手工路径：用户可以自己粘贴 cookie，并单独指定 User-Agent 与 TLS 指纹（ValidateCookie 端点、前端 CookieValidator.tsx）。
  • 服务端部署下 NullGuiAdapter 返回 CancelledWebViewSession.Instance，即自动采集在 Docker 下今天本来就不可用，用户只能走手工路径。

纯客户端下坏在哪三环

问题能不能解决
一登录窗口必须在客户端弹，但发起方是服务端能。标记 [RunsOnUserMachine]，采集由本地转发层在客户端执行，用客户端自己的 IGuiAdapter 弹窗

应对：客户端代发第三方请求的方案已被否决

所有者已否决"由客户端代发第三方请求"。 理由是决定性的：大量第三方请求本来就发生在服务端——增强器、下载器、订阅轮询等后台任务都是服务端自己按计划发起的，那些时刻客户端不一定开着。把这条链路的可用性绑在"客户端在线"上，等于让后台任务变得不可靠。

因此第三环没有彻底解法，第一版的做法是：

  1. 解决第一、二环（客户端弹窗 + 上报真实的 User-Agent 与 TLS 指纹）。
  2. 第三环如实提示，并把上面那张表的结论直接告诉用户——绝大多数家庭部署不受影响，云主机部署会受影响。
  3. 兜底沿用已有的手工粘贴路径：用户可以在服务端所在网络的任意一台机器上取得凭据后粘贴进来。这条路径今天就存在，不需要新做。

由哪一台客户端弹窗

所有者指出通常只有一个用户、多台设备，所以这个问题比想象中简单：

规则：谁发起，谁处理。 采集几乎总是用户在某台客户端上点了"登录"触发的，就由那台客户端弹窗，凭据原路返回。

9.2 拖拽本地文件进入媒体库

跨机器操作。要么上传，要么禁用。第一版禁用并给出明确说明：上传会引入进度、断点、磁盘配额、冲突处理一整套问题，不该和本设计捆绑。

9.3 依赖组件

视频处理等依赖组件安装在服务端，客户端不需要也不应该安装。界面上需要说明"安装在服务器上"，避免用户以为是在装到自己电脑上。
