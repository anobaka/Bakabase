# 本机纯服务端：部署、导入与升级

`Bakabase.Service` 可以独立提供 API 和网页，不需要安装桌面窗口。macOS Apple Silicon 可以直接运行 `osx-arm64` 程序；Docker 则运行 `linux/arm64` 容器，两者使用相同的数据格式。

程序与 AppData 分开保存：升级只替换程序，下次启动在原数据目录上执行必要的数据库升级。源码构建也采用这个方式，无需将日常数据放进源码目录、`bin/` 或发布目录。

## 从源码部署到当前 Mac

准备以下工具：

- `.NET 9 SDK`，版本按仓库根目录的 `global.json` 选择。
- Node.js 22 或兼容的新版本，Corepack，以及仓库 `src/web/package.json` 指定的 Yarn 4.9.2。
- Python 3.9 或更新版本、Git。

在仓库根目录执行：

```bash
git submodule update --init --recursive

# 程序发布目录；首次打开网页后选择独立的数据目录。
export BAKABASE_SERVER_HOME="$HOME/.local/share/bakabase-server"

python3 scripts/server.py build
python3 scripts/server.py run
```

浏览器打开 <http://127.0.0.1:34567>。服务以前台进程运行，按 `Ctrl-C` 停止。需要长期后台运行时，可将同一条 `run` 命令交给自己的进程管理器，并保留相同的程序目录和显式数据路径设置。

全新部署会先显示初始化页面，此时尚未打开主数据库。先选择是否从已有数据导入，再选择数据保存目录；导入时增加路径预检和修正步骤，最后检查并确认执行结果。不导入时仍为三步。每次只显示当前一步，返回修改会保留输入；最后一步说明来源、目标、路径修改数量、旧数据处理方式和何时执行。已有实例没有任何变更时，在目录选择后即可直接返回。不导入时，首次设置会创建新数据。原生服务未固定数据路径时，选择保存在默认位置的 `.redirect` 文件中；以后升级程序仍沿用该位置。已有数据库或有效 `app.json` 的老部署直接启动原来的库。

本机浏览器可以自动取得首次设置所需的凭据；其他访问方式使用启动日志中 `Server setup:` 后的链接（包含 `#setupToken=`）。Docker 不允许通过浏览器自动领取该凭据。首次设置凭据保存在默认数据入口的 `.bakabase-server-setup.json`，仅当前系统用户可读，提交成功后失效。初始化页面之外的应用接口在确认前返回维护状态。

若需要部署固定路径，设置 `BAKABASE_DATA_DIR` 或使用 `run --data-dir`；这种情况下初始化页面仍能创建空白库或导入来源，但不能更改目标位置。脚本未指定路径时不会代为设置该环境变量。

`build` 自动识别当前系统和 CPU：Apple Silicon 使用 `osx-arm64`，Intel Mac 使用 `osx-x64`。发布产物自带 .NET runtime，运行时不依赖 SDK。构建会检查服务端产物没有桌面 Shell 等依赖，且包含实际前端文件。

程序目录如下；每次成功构建都会保留一个新版本，失败构建不会切换当前版本：

```text
~/.local/share/bakabase-server/
├── current -> releases/20261008T...-commit-id
└── releases/
    ├── 20261008T...-commit-id/
    │   ├── bakabase-server
    │   ├── web/
    │   ├── release.json
    │   └── ...
    └── ...

~/Library/Application Support/Bakabase.Server/    # 数据独立保存
```

不设置 `BAKABASE_DATA_DIR` 时，macOS 的默认入口是上面的 `Bakabase.Server` 目录；Linux 使用 `$XDG_DATA_HOME/Bakabase.Server`，未设置 XDG 时使用 `~/.local/share/Bakabase.Server`。首次设置后，入口可通过 `.redirect` 指向选定的独立数据目录。一体版默认使用另一个目录 `Bakabase`，纯服务端不会默认打开一体版的数据库。

可显式指定路径、监听地址和端口：

```bash
python3 scripts/server.py --install-dir "/Volumes/Apps/bakabase-server" build
python3 scripts/server.py --install-dir "/Volumes/Apps/bakabase-server" run \
  --data-dir "/Volumes/Data/bakabase-server-data" \
  --bind 127.0.0.1 --ports 34567
```

`--install-dir` 是全局参数，放在子命令前。数据目录必须与程序目录分开，脚本会拒绝互相包含的路径，包括通过符号链接指向程序目录的路径。传给服务程序的额外参数可放在 `run -- ...` 后面。

本机部署默认仅监听 `127.0.0.1`。需要其他设备连接时，设置 `--bind 0.0.0.0` 或 `BAKABASE_BIND_ADDRESS=0.0.0.0`，并按实际使用需求配置远程访问。端口也可以通过 `API_LISTENING_PORTS=34567,34568` 设置。

### macOS 系统代理与 OrbStack

从旧机器导入后，先检查“配置 → 代理”。保存过的自定义代理会继续优先使用；例如旧机器的 `127.0.0.1:18888` 在容器中指向容器自身，不能代表 Mac 的代理。选择“使用系统代理”可以取消这项覆盖，并保留自定义代理列表以便以后切换。单个平台的代理覆盖仍单独生效。

原生 macOS 进程使用系统代理设置。OrbStack 的 `network_proxy: auto` 则在容器网络层透明跟随 macOS 系统代理及排除规则，容器无需填写宿主机代理端口，也无需另起同步服务或注入 `HTTP_PROXY`、`HTTPS_PROXY`。此行为由 OrbStack 提供，并不是 Linux 容器能直接读取 macOS 设置；其他 Docker 运行环境应按其自身的代理配置方式处理。参见 [OrbStack 代理说明](https://docs.orbstack.dev/docker/network#proxies)。

“不使用代理”只表示 Bakabase 不额外指定应用层代理，不能绕过宿主机的 VPN/TUN 或容器运行环境的透明代理。无论采用哪一种方式，都可使用配置页面的代理测试核实实际连通性。

Docker Compose 开放局域网访问时，在部署使用的环境文件中设置 `BAKABASE_BIND_ADDRESS=0.0.0.0` 并重新创建容器，再通过 Mac 的局域网 IP 和 `34567` 端口访问。应用中的远程访问设置也必须允许该设备；原有的配对或访问限制不会因修改端口绑定自动改变。OrbStack 还需要允许将容器端口暴露给局域网。

## 导入已有 AppData

优先采用“复制导入”：首次初始化时选择“从已有数据导入”；已有服务则从“配置 → 系统信息 → 导入已有数据”进入同一个设置页面，先选择原数据目录，再决定保留当前保存位置还是更换目录。来源可以是一体版或其他服务端实例。原数据会保留，试运行服务端不会直接修改唯一的旧数据。

导入前先停止所有使用来源目录的 Bakabase 进程，无论来源是一体版还是其他服务端。对完整源目录做一次停机备份；不要只复制 `.db` 文件，配置、封面、缓存及 SQLite 的关联文件也属于数据的一部分。若旧版把 AppData 存在安装目录内，应选择那个实际的 AppData 目录；若设置过重定向，以旧版设置页面显示的**实际数据目录**为准。

选择的路径是**服务端看到的路径**。原生部署可以直接选择当前 Mac 的目录；Docker 需要先把源目录挂载进容器，再选择容器内路径。如果 Docker 中选择 `/import`，而旧 AppData 实际位于 `/Users/me/Library/Application Support/Bakabase`，在“原 AppData 路径”中填后者，帮助旧版数据库里的绝对封面路径重定位。此选项只描述历史路径，不要求它在容器里存在，也不会替换媒体库的原文件路径。

校验并确认后，Setup 会保存执行计划。首次初始化直接开始导入；已有服务由协调器请求业务进程正常退出，确认进程退出及数据锁释放后自动开始维护，无需手动重启。停止耗时过长时会继续等待，不会强制终止后立即替换数据。保留当前目录时，先复制源数据、检查 SQLite 完整性、备份当前服务端数据，再安装到当前目录。选择新目录时，直接将来源导入新的空目录，校验成功后才切换入口，原来的当前目录保留。固定设置了 `BAKABASE_DATA_DIR` 也可以导入，但保存位置由部署配置决定。

导入进度页面与原服务使用同一个地址和端口。确认导入后保留进度页；业务停止和端口交接期间页面会自动重连，维护 worker 开始复制后显示当前阶段和进度。无需另开端口。扫描文件、复制、校验数据库、备份旧数据、安装以及启动服务是不同阶段，复制完成不等于整个服务已就绪。

进度页显示阶段轨迹、文件数、字节数、当前文件和本次执行耗时；复制过程中还显示平均速度和预计复制剩余时间。这个预计时间不包括之后的完整性检查和数据库升级。服务响应、存活心跳与工作进度分开显示：数据库校验期间暂时没有文件数变化不代表失败。服务初始化完成后才显示完成并提供进入应用的按钮。

默认启动的是不打开业务数据库的轻量 Setup 协调器；业务和维护 worker 是同一发布包内的独立子进程。在线时业务只转发受限的 Setup/进度接口，维护期间由协调器接管相同对外端口。worker 异常退出后协调器仍保留失败页面。整个协调器被停止或网络中断时，页面保留最后确认的状态并自动重连，不会把断线推断为成功或失败。下次启动会根据保存的记录恢复。监控链接没有权限时会提示重新获取链接。

进度页使用本次导入专用的查看凭据。凭据位于页面链接的 `#` 片段中，仅用于读取该次操作状态；不要把含此片段的链接发给无关人员。若关闭了页面，可使用启动日志中 `Server maintenance:` 后的链接恢复查看。查看进度不会提前启动主应用，也不能从维护页面执行普通资源操作。

导入到当前目录时，导入前的服务端数据保存在 `<AppData>/backups/appdata-imports/<导入编号>/`，已有的版本备份留在原 `backups/` 目录。导入到新目录时，旧数据及其历史备份留在原来的当前目录。两种情况下，来源目录的历史 `backups/` 都不重复复制，仍保留在来源中。导入期间意外结束进程，再启动会按操作记录恢复：未完成的复制阶段会重新复制，备份或安装阶段会继续处理尚未移动的项目；这不是文件内容的字节级断点续传。导入并更换目录还会在默认入口保留 `.bakabase-relocate.json`，与新目录的导入记录共同恢复，验证完成前不切换入口。导入未完成时不会启动应用去读取部分数据。应保留源目录直到导入结束且功能验证通过。

导入失败时，服务保留只读进度页显示错误，不启动主应用。排除源目录不可访问、源实例未停止、磁盘空间不足等原因后，手动停止并重新启动服务重试。容器仍在运行以提供错误页面，因此不会仅因这类失败就自动重启。

迁移时还需要注意：

- 数据库里的媒体原文件通常位于 AppData 之外。导入 AppData 不会复制整个媒体库。原生 Mac 沿用原来的媒体路径最方便；Docker 必须挂载媒体目录，并确认库中的路径在容器内仍有效。
- 从 Windows 迁到 Mac，或从原生 Mac 切到 Docker 时，盘符、路径和外部工具可能不同。先验证目录、缩略图、播放和下载功能，再开始日常使用。
- Docker 会拒绝导入显式禁用了远程访问的数据，以免导入后无法从浏览器访问。可先原生导入一个副本，配置好远程访问和配对，再停止原生服务并把该副本导入 Docker；导入不会自动放宽源数据的访问权限。
- 初次试运行建议暂停计划任务、下载和自动文件整理；独立 AppData 仍可能指向同一批真实媒体文件。
- 只让一个实例拥有同一个有效 AppData。不能同时用一体版和纯服务端打开同一套数据，也不能让原生进程和容器同时使用它。
- 导入会保留原实例的设备身份。迁移完成后不要再同时启动旧数据副本作为另一个设备；确实需要长期维护独立副本时，应为副本重置设备身份。
- 新版第一次启动会执行数据库迁移。保留原始备份，旧程序未必能读取升级后的数据库。

### 导入时预检与修正路径

导入向导会在后台只读扫描来源数据库中的文本值及配置 JSON，识别 Windows 盘符、UNC 和 POSIX 绝对路径，包括嵌套 JSON、StandardValue 转义列表及历史播放引用。日志、媒体文件、缓存文件内容和历史备份不参与扫描。预检要求来源已停止，SQLite WAL 已 checkpoint；它不会修改来源或提前关闭当前业务进程。

路径聚合成按需展开、分页加载的目录树，各层显示引用数量。点击任一层添加“旧前缀 → 新前缀”规则，可对整盘重映射，再为个别子目录添加更具体的规则。按目录边界和最长前缀匹配，Windows 路径不区分大小写，POSIX 路径区分大小写。预览显示会改变及保持原样的引用数和限量示例；没有映射规则也可以明确保留全部原路径。来源或保存位置变化后需要重新预检，修改规则后需要重新预览。目标可通过服务端目录浏览器选择；Docker 使用容器内挂载路径。预览不逐项探测 NAS 文件是否存在，不复制媒体、不创建媒体目录，也不自动增加挂载。

映射只作用于复制出来的暂存数据，SQLite 事务及完整性检查通过后才安装。来源指纹在预检与实际执行之间必须一致；不同路径映射到同一个目标等冲突会拒绝执行。复制或映射中断后重新从来源生成暂存副本，避免重复映射已经修改过的数据。开始备份或安装后则沿持久化记录继续，不重新映射。该执行计划采用新的版本号，旧 Setup 不会误将带映射的计划当作普通导入执行。

未提交的目录选择及映射规则自动保存到默认数据入口的 `.bakabase-setup-draft.json`，采用临时文件、刷新磁盘、原子替换，在 Unix 上仅当前用户可读写。草稿不包含访问凭据，不写入来源目录或浏览器存储，不需要业务数据库。重开向导自动恢复编辑内容，但仍需重新预检和最终确认。成功安装映射后的数据会删除对应草稿；失败时保留。用户也可点击“清空已保存草稿”，取消扫描并删除草稿及其临时文件，当前媒体库不受影响。草稿不会混入导入数据、迁移副本或版本备份。

### 跨平台离线路径转换（命令行）

Windows 盘符或旧 NAS 挂载路径需要改成新服务端路径时，可在**已停止使用的导入副本**上运行 `scripts/remap_appdata_paths.py`。先保存完整原始备份，再准备 JSON 映射文件；键是旧目录前缀，值是新服务端实际可见的绝对路径，例如：

```json
{
  "D:\\Media": "/Volumes/Media",
  "C:\\Bakabase\\AppData": "/data"
}
```

默认只预览并输出报告。确认报告后，增加 `--apply` 和一个位于数据目录之外、尚不存在的备份目录；工具会在修改前保存涉及的数据库、关联文件及配置：

```bash
python3 scripts/remap_appdata_paths.py --data-dir /path/to/offline-copy \
  --mapping-file /path/to/path-mappings.json --report /path/to/preview.json

python3 scripts/remap_appdata_paths.py --data-dir /path/to/offline-copy \
  --mapping-file /path/to/path-mappings.json --report /path/to/applied.json \
  --apply --backup-dir /path/to/new-remap-backup
```

转换按目录边界匹配，优先使用最长前缀，并按 SQLite 列类型解析 StandardValue 转义格式和嵌套 JSON。没有映射的盘符（例如 `E:`、`H:`、`I:`）保持原样，记录在报告中，需确认它们是否仍有用途。工具不会复制媒体文件或自动增加容器挂载。

可另加 `--invalidate-missing-covers --runtime-data-dir /data`，使导入副本中确实缺少对应文件的派生封面缓存失效，以便重新生成；它不删除用户附件。原生部署时将 `/data` 换成目标实例实际使用的数据目录。转换完成后再将副本作为 Setup 的导入来源，不要对正在运行的数据目录执行此工具。

## 只更改现有库的数据目录

未通过环境变量固定路径的原生服务，可以从配置页面的数据路径修改入口进入同一套维护页面。第一步选择“不导入”，第二步选择“更换数据保存目录”及一个新的空目录；系统搬迁的是当前数据，保留其数据库、配置、封面、历史备份和日志。如果第二步也选择“使用当前数据目录”，可直接完成并返回应用，不会排队或要求重启。目标不能与当前目录相同，也不能互相包含。Docker 或显式设置了 `BAKABASE_DATA_DIR` 的部署会拒绝更换目录，应在停机后调整挂载或部署配置。

确认后保存计划，Setup 自动停止业务子进程并等待实际退出，然后启动独立维护 worker。执行期间同时持有源和目标的数据锁，复制及数据库检查通过后才切换入口的 `.redirect`；进度页仍使用同一个查看凭据。新的数据目录启动并完成初始化后才显示完成，后续升级和重启会继续使用该位置。

原目录里的库文件会保留为回退副本，不会自动删除。确认新库及媒体路径正常后再自行处理旧副本，不要同时启动两套相同设备身份的数据。需要额外磁盘空间容纳完整副本，包括原来的历史备份。

确认前可以返回修改选择；确认后自动执行，不再通过旧业务接口取消计划。已经开始复制后应按进度页提示停止并重启 Setup 恢复，复制阶段会重新复制，安装阶段按记录继续。`.bakabase-relocate.json` 保存在数据入口；不要在操作未完成时手动删除它或混合源、目标文件。

## 源码更新与快速测试

先在仓库中完成需要测试的代码更改，或自行切换到希望部署的 commit。部署脚本不会自动 `git pull`、切分支或更新子模块到远端最新版本。

仅改了后端时，可以复用已构建的前端：

```bash
python3 scripts/server.py build --web-dir src/web/dist --no-activate
```

`--web-dir` 需要包含构建好的 `index.html`。如果改了前端或接口对应的前端代码，使用普通 `build` 同步重建前端。源码中的未提交改动会参与构建，`release.json` 记录 commit、工作区是否有改动、目标架构和构建时间。

一次完整升级按以下顺序进行：

1. 构建新版本。推荐先用 `build --no-activate`，保持当前选择不变；旧进程仍可运行。
2. 停止旧进程或进程管理器，确认 AppData 已不再写入。
3. 将完整 AppData 备份到程序目录和数据目录之外。
4. 使用 `list` 查看新版本名称，再 `activate` 选中它。
5. 重新 `run`，检查网页、资源数量和正在测试的功能。

```bash
python3 scripts/server.py build --no-activate

# 此时先停止旧服务，再备份。以下路径变量与部署时保持一致。
: "${BAKABASE_DATA_DIR:?请先设置实际 AppData 路径}"
backup="$HOME/Bakabase-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup"
rsync -a --exclude='.bakabase.lock' "$BAKABASE_DATA_DIR/" "$backup/appdata/"

python3 scripts/server.py list
python3 scripts/server.py activate <list输出的新版本名称>
python3 scripts/server.py run
```

备份示例要求 `BAKABASE_DATA_DIR` 是实际数据目录。如果它是包含 `.redirect` 的入口目录，应另外备份入口和设置页面显示的实际目录。`.bakabase.lock` 是运行期排他锁文件，备份时跳过；不要复制一个仍在使用中的数据库。

不加 `--no-activate` 时，成功构建会自动选中新版本，但不会终止或重启旧进程。正在运行的进程使用其具体版本目录，不会因为 `current` 改变而读到另一版本的网页。所有历史程序版本都会保留，脚本不自动清理。

## 回滚

`activate <旧版本名称>` 只切换程序，不会把数据库降级。尚未启动过新程序时可以直接切回；新程序已经完成数据库迁移后，应停止它，保留当前数据的副本，再把**升级前的完整 AppData 备份**恢复到原目标路径，最后选择配套的旧程序启动。

不要将备份覆盖合并进一个仍运行中的目录，也不要保留混合了新旧文件的 AppData。恢复之前确认备份版本，并保留失败版本的数据，方便后续排查。

这种源码部署与 Docker 升级的共同点是：**替换程序，保留独立数据，再执行迁移**。它不依赖桌面版的安装包更新器，也不会自动追踪远端发布。Docker 的挂载与 ARM64 镜像使用方法见 [Docker 部署说明](docker-installation.md)。

## 验证部署脚本

```bash
python3 -m unittest discover -s scripts/tests -p 'test_server.py' -v
```

这些检查只使用临时程序和数据目录，覆盖路径带空格、切换版本保留旧程序、拒绝数据与程序重叠、拒绝越界版本指针以及构建失败不影响当前版本。

已有本机发布产物后，可另行执行独立 Setup、业务和维护 worker 的真实进程冒烟检查：

```bash
python3 scripts/tests/server_setup_process_smoke.py
```

该检查以普通 Unix 用户启动临时源实例和目标实例，验证首次初始化、独立业务子进程、确认后自动停止业务并完成导入、源文件字节不变，以及强制结束复制 worker 后父进程仍能提供失败进度。它还检查父进程正常退出和意外退出时的子进程回收，不读取日常数据。可用 `--release <版本目录>` 指定产物，或用 `--service-dll <编译后的 Bakabase.Service.dll>` 配合 PATH 中的 dotnet 测试框架依赖构建；成功后自动清理临时数据，`--keep-data` 可保留证据，失败时保留日志。测试结束总会停止其创建的服务进程。

`server_import_smoke.py` 保留了旧版需要手动重启的接口检查，仅用于对应旧产物；当前独立 Setup 的自动维护流程使用上述新脚本。复制、权限、组合导入和中断恢复的细粒度边界由后端回归测试覆盖。

## 一体版首次初始化

一体版首次启动也会在创建业务数据库之前打开同一套初始化页面，页面显示在原生窗口内，可通过系统目录选择器选择 AppData 目标目录和可选的导入源。确认后继续初始化；导入过程显示同样的复制和备份进度，完成后进入主界面。若设置了 `BAKABASE_DATA_DIR`，目标由环境变量固定，仍可选择导入源。

关闭尚未确认的初始化窗口会退出，不创建业务数据库。已经确认后中断导入，下次启动会根据保存的状态恢复。导入仍是复制源 AppData，源目录保持不变；应先关闭使用源目录的 Bakabase 实例。已有数据库或有效版本配置的旧用户继续使用现有目录，不会被要求重新初始化或迁移。

## 统一数据设置向导

首次启动提供数据保存位置，以及创建空白媒体库或导入已有 AppData 的选择。已有实例从系统信息的修改路径或导入入口进入同一向导，不提供创建空白库操作；改变路径保留当前库，导入则从另一个已停止的 Bakabase 实例复制数据并备份当前库。来源可以是一体版或服务端，不限安装形式，仍须通过版本和 SQLite 完整性检查。

界面统一称为“数据保存目录”和“导入已有数据”。首次预填默认目录，已有实例预填当前目录；路径未改变时不允许提交搬移。默认通过“选择文件夹”操作，必要时可切换到手动输入。桌面首次设置使用系统目录选择器，网页使用轻量维护服务提供的目录选择器；网页列出的是服务端所在设备的文件夹，Docker 中则是容器可见的文件夹。选择目标位置时可以另填一个新文件夹名称，选择和浏览只计算路径，确认配置后才创建目录。目录列表不返回文件内容，且仅在本次设置凭据有效时可访问。

该页面由无业务数据库依赖的独立 Setup 协调进程提供；复制和切换由独立 worker 执行，业务进程在 worker 成功退出且计划完成后才启动。三个角色使用同一发布包，不需要安装系统级守护进程。桌面只为同一套网页增加窗口和原生目录选择器。Docker 中协调器保持容器运行，只停止、启动业务和 worker 子进程；停止容器时转发退出并回收子进程。部署固定目录的实例允许导入，但必须通过部署配置更改保存位置。

一体版重复启动会唤起已有业务窗口。桌面更新器等待整个协调进程退出后再替换安装文件；普通源码重启也保留正确的 DLL 入口和父进程等待关系。移动端 Flutter 客户端不使用本地 Setup 进程入口。
