# 初始化与数据维护（Setup）

一体版桌面应用和纯服务端共用同一套 Setup，用于首次选择数据保存目录、从其他 Bakabase 实例导入数据，以及更改现有实例的数据保存位置。这里的“数据”包括数据库、配置、封面和附件等应用数据；位于数据目录之外的媒体原文件不会随导入自动复制。

## 进入向导

首次启动且没有已有数据库或有效 `app.json` 时，先显示 Setup，确认前不启动业务服务或创建业务数据库。一体版在原生窗口内显示该页面；纯服务端通过浏览器访问。已有数据库或有效版本配置的老用户继续使用原目录，不需要重新初始化。已有未完成的数据操作则先恢复该操作。

进入应用后，可从“配置 → 系统信息”的“导入已有数据”或数据保存目录的“修改”入口打开同一向导。打开向导、浏览目录和预检不会关闭当前业务进程；只有最终确认需要执行的数据操作后才开始停机维护。

向导按以下顺序操作：

1. 选择是否从已有数据导入；来源可以是一体版或其他服务端的数据目录。
2. 选择数据保存位置，默认填入首次使用的默认目录或现有实例的当前目录。
3. 导入时进行路径预检、配置可选的前缀映射，并查看修改预览。
4. 核对来源、目标、路径修改和旧数据处理方式，再确认执行。

不导入时省略路径预检，保留三步流程。已有实例不提供“创建空白数据”的操作；不导入且沿用当前目录时直接返回应用，无需停机。更改现有数据目录时，目标必须是新的空目录，且不能与当前目录相同或互相包含。

桌面首次设置可以使用系统文件夹选择器。网页中的文件夹选择器浏览的是**服务端所在设备**的目录，Docker 中则是容器可见的目录；它不使用浏览器上传文件夹来推断本机完整路径。也可以切换到手动输入。选择时可以填写一个新文件夹名称，确认前只计算目标路径，不创建数据目录。

设置了 `BAKABASE_DATA_DIR` 或运行在容器中时，数据保存位置由部署配置固定，Setup 可以导入已有数据，但不能修改这个位置。Docker 导入来源和媒体目录必须先由部署者挂载进容器；向导不会添加或修改容器挂载。

Docker 的目录浏览器只列出已挂载的持久存储目录，手动输入的导入来源、目标和路径映射目标也使用同样的检查。只读目录仍可作为来源选择，写入权限由文件系统决定。原生 server 与一体版使用操作系统目录，不要求挂载。

## 进程、文件锁和更新

Setup 协调器、业务服务和维护工作进程使用同一发布包，分别运行在独立进程中，不需要另外安装系统级守护进程。

| 角色 | 负责的工作 |
| --- | --- |
| Setup 协调进程 | 保存设置、提供 Setup 和进度页面、管理子进程，不初始化业务数据库 |
| 业务进程 | 正常运行数据库、后台任务、API 和主界面 |
| 维护工作进程 | 持有数据目录锁，执行复制、校验、路径映射、备份和安装 |

确认操作后，协调器先保存计划并请求业务进程正常退出，等待其实际退出、释放数据库连接及文件锁，再启动维护工作进程。业务退出耗时较长时会继续等待并显示停止阶段，不会强制终止后立即覆盖数据库。维护进程仍需成功取得数据目录锁，无法取得时拒绝处理。

纯服务端在业务运行时转发受限的 Setup 接口，维护期间由协调器接管同一对外地址和端口。端口交接期间进度页会自动重连。维护工作进程失败时，协调器继续提供失败状态；只有数据操作成功完成后才重新启动业务进程。停止协调器或容器时会通知并回收子进程。

桌面重复启动同一数据目录会唤起已有窗口。桌面更新器等待协调进程退出后才替换安装文件，避免业务子进程已经退出、协调进程仍加载旧文件时发生覆盖。通过 `dotnet` 启动的桌面程序重启时保留 DLL 入口和前驱进程等待关系。

Setup 不负责下载或替换 Docker 镜像，也没有网页“一键升级”按钮。纯服务端升级由部署者替换镜像或程序发布目录，再使用原来的独立数据目录启动。切换程序版本不会自动降级数据库。

## 导入预检和路径映射

导入前先正常关闭使用来源目录的所有 Bakabase 实例，并保留完整来源备份。选择实际存储数据的目录；旧实例使用重定向时，以旧实例设置页面显示的有效数据目录为准。不要仅复制一个数据库文件代替完整数据目录。

预检以只读方式扫描来源 SQLite 数据库的文本值及配置 JSON，识别 Windows 盘符、UNC 和 POSIX 绝对路径，包括嵌套 JSON、StandardValue 转义列表及历史播放引用。日志、媒体文件、封面和附件的文件内容、临时文件及历史备份不参与路径扫描。预检不会修改来源；存在尚未 checkpoint 的非空 SQLite WAL 时会拒绝扫描，应先让来源实例正常退出并完成数据库关闭。

扫描结果聚合为按需展开的目录树。用户可以为任意目录层级添加“旧前缀 → 新前缀”规则，例如把整个 `Y:/` 映射到服务端可见的 `/Volumes/nas-bakabase`，再为某个子目录指定更具体的目标。规则按目录边界和最长前缀匹配，Windows 路径不区分大小写，POSIX 路径区分大小写。没有匹配规则的路径保持原样，也可以不添加规则，明确保留全部原路径。

预览和目录树有明确的返回数量限制：

- 修改预览最多显示 **20 条示例**；统计覆盖全部已扫描路径和引用次数。
- 目录树每次只返回所展开层级的 **最多 200 个节点**，更多节点分页读取。
- 实际应用处理全部匹配引用，不受上述展示数量限制。

这些限制避免把完整路径列表传到浏览器，但不代表服务端内存恒定：当前实现仍在内存中保存去重后的路径和排序索引，预览会遍历全部路径并检查映射目标冲突。数据量增大时，扫描和预览需要更多时间与内存。

规则最多 256 条；重复来源、冲突目标、规则循环或不同路径映射成同一个目标会被拒绝。修改来源或保存位置后需要重新预检，修改规则后需要重新预览。预览不逐项检查 NAS 上的目标媒体是否存在，也不创建目标媒体目录；应结合服务端目录浏览器和实际挂载确认路径。

## 复制、替换和中断恢复

Setup 会保留来源数据，并将映射应用到复制出来的暂存数据。预检记录的来源指纹需与执行时来源及复制出的数据一致，防止确认后来源发生变化。SQLite 映射在事务中执行，配置文件通过临时文件替换；映射、数据库完整性检查等步骤通过后才进入安装。

导入到当前保存目录时，先复制和校验来源，再把原数据备份到 `<数据目录>/backups/appdata-imports/<导入编号>/`，最后安装导入数据。已有版本备份保留，来源中的历史 `backups/` 不重复复制。导入并更换保存位置时，把来源导入新的空目录，成功后才切换入口的 `.redirect`；原来的当前数据目录继续保留。

仅更改现有实例保存位置时，复制当前数据及历史备份和日志，校验通过后切换 `.redirect`。旧目录不会自动删除；确认新目录正常后再自行清理。两种操作都需要足够空间容纳新副本以及必要的旧数据备份。

复制或路径映射阶段中断后，下次启动会重新从来源生成暂存数据，避免重复映射已修改的路径。进入备份或安装阶段后，按持久化记录继续处理尚未完成的项目。这是按阶段恢复，不是文件内容的字节级断点续传。来源应保持关闭且可访问，直到操作和功能验证结束。

进度页面显示当前阶段、文件和字节计数、当前文件、耗时；复制时还显示平均速度及预计复制剩余时间。该预计时间不包含后续数据库检查和业务启动。服务存活与工作进度分别呈现，数据库校验时计数不变不等于失败。业务完成初始化后才显示完成。

网络断线时页面保留最后确认状态并重连，不把断线推断为成功或失败。失败时先查看原因、保留来源和现有数据，排除权限、空间或目录不可访问等问题后，正常停止并重新启动 Setup 或容器以恢复。不要手工删除未完成操作的记录或混合源、目标文件。

导入保留来源的设备身份及相关配置。迁移完成后不要同时运行旧副本作为另一个设备；需要独立副本时使用产品提供的身份重置流程。导入不自动放宽远程访问限制，Docker 会拒绝显式关闭远程访问的来源配置。新版业务启动可能继续执行其数据库迁移，回退程序时需使用匹配版本的完整数据备份。

## 草稿和访问凭据

目录选择和路径映射编辑自动保存到数据入口（anchor）下的 `.bakabase-setup-draft.json`。草稿只记录编辑内容，不包含 Setup/进度访问凭据，也不保存已确认的预检结果。它不写入来源目录、业务数据库或浏览器存储。

草稿使用临时文件、刷新磁盘和原子替换；Unix 上仅当前用户可读写。重新打开向导会恢复输入，但仍需要重新预检和最终确认。成功安装对应计划后会清理匹配的草稿，失败时保留；用户也可以点击“清空已保存草稿”，取消当前扫描并删除草稿及其临时文件，不影响当前媒体库。草稿不会进入复制、导入或自动版本备份。

Setup 和进度页使用不同的访问凭据。进度凭据只能查看本次操作状态，不能提交数据变更。首次服务端设置可使用启动日志中 `Server setup:` 的链接；本机浏览器可在符合本地访问条件时领取设置凭据，Docker 禁止自动领取。维护查看链接可从 `Server maintenance:` 日志恢复。链接的 `#` 片段包含凭据，不应分享给无关人员。

## 验证

后端回归测试位于 `src/tests/Bakabase.Tests/`，覆盖导入/转移、复制权限、数据库与路径映射、草稿、HTTP 权限、真实目录锁、进程协作及桌面关闭/更新。前端页面测试位于 `src/web/src/test/setup-page.test.ts`、`progress-page.test.ts` 和系统信息入口的测试目录。

以下三个脚本组成真实进程验证工具，均使用临时源实例和目标实例，不读取日常数据：

| 脚本 | 用途 |
| --- | --- |
| `scripts/tests/server_import_smoke.py` | 共享 HTTP、临时实例和摘要工具；自身入口保留旧版手动重启协议，仅适用于对应旧产物 |
| `scripts/tests/server_setup_process_smoke.py` | 当前独立进程流程：首次初始化、自动停止/重启业务、来源不变、维护进程异常退出、协调器和子进程退出 |
| `scripts/tests/server_preflight_smoke.py` | 真实预检和映射导入、草稿重启恢复与清理、当前业务保持运行、来源摘要与导入结果验证 |

在 Unix 环境使用已经构建的 Service DLL 验证当前流程，确保 `dotnet` 位于 `PATH`：

```bash
python3 scripts/tests/server_setup_process_smoke.py \
  --service-dll /absolute/path/to/Bakabase.Service.dll

python3 scripts/tests/server_preflight_smoke.py \
  --service-dll /absolute/path/to/Bakabase.Service.dll
```

`server_setup_process_smoke.py` 也支持 `--release <包含 bakabase-server 可执行文件的发布目录>`；预检脚本使用 `--service-dll`。成功时自动清理临时数据；添加 `--keep-data` 保留证据，失败时保留日志。脚本结束会停止自己创建的服务进程。桌面安装包更新、Windows 文件占用及移动端真机行为仍需在相应平台单独验证，Unix 进程测试不能代替这些发布检查。
