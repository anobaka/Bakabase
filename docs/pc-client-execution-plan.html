三条最重要的盘点结论，它们改变了设计文档的前提：
  1. RuntimeMode 是编译期常量（AppService.cs:250-258 用 #if RUNTIME_MODE_*，常量来自 Bakabase.Infrastructures.csproj:7，由 _build.yml:147 的 -p:RuntimeMode= 传入）。决策 06 之后，"一体版还是纯客户端"同样在构建期决定，但用与它并列的独立属性 -p:AppFlavor=，而不是往 RuntimeMode 里加取值——它现在的含义是"我是哪个平台的服务端宿主"，加进去会变成正交概念相乘（§5.1）。

§2全局硬规则

这些规则由代码事实推出，违反任何一条都会直接破坏一体版。实现期间每次评审都对照它们。

#规则为什么（代码事实）
R1客户端程序集只能被 src/apps/Bakabase.Client.App/ 引用；Bakabase.Shell 不得引用任一宿主实现；Bakabase.Service 与任何模块绝不反向引用它Docker 镜像是 COPY . . 整个 Service 发布目录（docker/Dockerfile:5）。一旦 Service 引用客户端，转发层、YARP 都会进入服务端进程与镜像。决策 06 之后这条从纪律变成结构：一体版入口不引用 Bakabase.Client，两者不在同一张引用图上，R2–R4 由引用图自动满足（那三条的扫描范围都是"入口程序集及其引用程序集"）
R2客户端程序集里不得定义 Controller 子类；本地端点一律用最小接口（MapGet / MapPost）MVC 会自动发现入口程序集及其引用程序集里的控制器（Bakabase.Cli/Program.cs:37 需显式 AddApplicationPart 正说明范围由入口决定）。一体版的 AddMvc 会把客户端控制器挂进 Kestrel：同路由的会触发 AmbiguousMatchException，直接破坏一体版播放端点
R3客户端选项类不得打 [Options] 特性；用手工构造的 OptionsDescriber 注册ConfigurationRegistrations.DiscoverAllOptionsDescribers 扫描入口程序集引用的全部程序集（ConfigurationRegistrations.cs:43-62）。一体版会把客户端选项注册进容器、在一体版 configs 目录挂文件监视，并经 WebGuiHub.GetInitialData 推给一体版前端
R4客户端程序集里不得定义 IPredefinedBTaskBuilderAddBTask 扫描 AppDomain 全部程序集（BTaskExtensions.cs:22-25）
R5客户端组合根不得调用 AddRemoteAccess，不得继承 AppHost / AppStartupAddRemoteAccess 注册的 RemoteAccessDiscoveryService 会用 mDNS 与固定 UDP 端口 33333 把客户端广播成服务器；AppHost.CreateHost 私有且固定监听 0.0.0.0（AppHost.cs:200、213），AppHost.Start 无条件迁移 LogDbContext（:366），AppStartup 无条件注册 SQLite 日志库与单页应用托管（:89、:95-97、:167-192）
R6本地转发层只绑定 127.0.0.1，并校验 Host 头它会用设备密钥代签一切发出的请求。监听所有网卡等于把用户的配对身份交给局域网；不校验 Host 则 DNS 重绑定可从任意网页驱动它
R7一体版 Program.cs 逐字不变；客户端入口的第一条语句必须是 AppDataAnchor.Use(...)；一切新增的闸门检查必须晚于 RemoteAccessMiddleware.cs:52 的回环直通AppService 有显式静态构造函数（AppService.cs:184-216），第 202 行就建目录、跑旧版迁移、开日志文件，而它会在任何静态成员被引用之前执行——所以锚点入口不能挂在 AppService 上（见 §5.1 陷阱一）。回环直通是一体版零影响的基石
R8子模块改动只做加法：新入口默认不生效、旧签名委托到新重载、纯搬移不改行为；每处配现有测试或新增测试决策 1 的前提
R9服务端拒绝集合 ≠ 转发层拦截集合：拦截集合 = [RunsOnUserMachine] 集合 + 一份显式覆盖表有些端点服务端不能拒绝远程调用但客户端必须本地处理（/tampermonkey/script、/remote-access/context、PATCH /options/app 的字段拆分、/app/restart 的客户端语义）。见 §5.10
R10设备密钥、配对码、签名密钥永不进入任何 [Options] 类型所有 [Options] 对象在 /hub/ui 连接建立时整体推送（WebGuiHub.cs:112-119）、变更时向 Clients.All 广播（WebGuiHubConfigurationAdapter.cs:35）。85e2c05 之前的旧实现正好踩在这条路径上
R11两个入口的 SingleInstanceId 必须不同BakabaseHost.cs:36 的 SingleInstanceId => "Bakabase" 推出互斥体 Bakabase_SingleInstance_Mutex 与管道 Bakabase_SingleInstance_Pipe（AppHost.cs:63-64）。同名就意味着客户端与本机一体版不能同时运行，而"一机双跑"是已批准的场景。客户端宿主用 Bakabase.Client
R12客户端安装包不携带网页前端前端由服务端下发（§5.6），连接前的界面是原生 ConnectView。所以客户端的构建腿跳过 _build.yml:148-152 的前端下载步骤。带上会白白增加体积，还会制造"本地前端与服务端前端谁生效"的歧义

命名边界整理（2026-09-11，纯重命名，产物零变化）：起因是一个问得很准的疑问——“为什么界面算 Shell 不算 Client”。答案是这两个名字根本不在同一根轴上：Shell 是层次词（外壳），Client 是角色词（网络关系的一端），两者不构成划分，所以那个问题当然没有答案。真正在划分的轴只有一根：server 在不在本进程。于是：Bakabase.Client → Bakabase.Client.Remoting（工程、程序集、命名空间三者一致；它装的是“server 在别的机器上”才需要的东西，不是“我是客户端”）；src/apps/Bakabase → Bakabase.App（与 Bakabase.Client.App 对称，程序集名仍是 Bakabase——可执行文件名写在每个已安装的 Velopack 清单里，改名会让存量用户升不上去）；Bakabase.Shell 的 RootNamespace 由 Bakabase 改为 Bakabase.Shell（此前它的类型叫 Bakabase.Windows.MainWindow，读代码时根本看不出属于 Shell；XAML 与 AssetLoader 认的是程序集名，avares://Bakabase.Shell/ 不受影响）；ITrayIconController 从 Bakabase.Abstractions 挪到 Bakabase.Infrastructures 的 Components/Gui/，与 IGuiAdapter 同处——它是纯图形端口，不含任何领域类型，原先那个位置是 Abstractions 下唯一的 Gui 文件。

两处因此需要别名：两个入口工程的命名空间（Bakabase.App / Bakabase.Client.App）与外壳的 App 类同名，未限定的 App 会绑到命名空间上，改用 using ShellApp = Bakabase.Shell.App;。
回归修复：一机双跑时客户端端口会随启动顺序漂移（2026-09-12）。LoopbackPortAllocator.PreferredPort 原本是 34568，注释还写着"刻意避开服务端端口"——但 BakabaseHost.DefaultAutoListeningPortCount => 3，服务端从 34567 起连取三个空闲端口并绑在 0.0.0.0 上（因而也占住 loopback），34568 恰恰是它的第二个端口。于是先开谁谁拿到：先开客户端得 34568，先开一体版则被挤到 34570。端口是浏览器 origin 的一部分，这正是该分配器存在的理由所要防的"设置怎么没了"。

两处修正：一，偏好端口移到 34600，并把 AllInOneWindowStart = 34567 也命名出来，由 The_preferred_port_clears_the_all_in_ones_own_window 锁住二者的间距（AutoListeningPortCount 用户可调，所以留的是 33 个端口的余量而不是一格）；二，新增 LoopbackPortMemory（客户端数据目录下的 host.json），记住实际绑上的那个端口、下次优先复用——否则某个无关程序临时占用偏好端口，客户端会在它退出后又走回去，等于换两次 origin。端口在宿主构建期就要定，那时还没有容器，所以它是一个裸文件读写而不是 [Options]；读写失败一律吞掉（端口那时已经选好，为了一个缓存而拒绝启动是拿致命换瑕疵）。
发布产物与「其他设备」页（2026-09-12）：起因是两个真实问题 —— release note 的下载区完全没有客户端（包传了，但正文一个链接都没有，只能滚到 Assets 里翻），以及文件名说不出「哪个是我要的」（Bakabase-Setup-…exe 与 bakabase-…zip 大小写不一、Bakabase.Client-Setup-… 与 bakabase-client-…zip 分隔符不一，且都没说 zip 是免安装版）。

三处改动：一，文件名统一成 产品-版本-平台-形态（Bakabase-{v}-win-x64-Setup.exe / Bakabase-Client-{v}-win-x64-Portable.zip），GitHub 资产与 CDN archives 用同一个名字 —— 此前 CDN 上是 vpk 原名（Bakabase-beta-Setup.exe，不含版本与平台，且随渠道变化），两边名字不同正是清单没法可靠生成的原因。能改的只有这两处副本：Velopack 的 --packId、主 exe 名、以及 releases/{rid}/ 下 vpk 自产的 RELEASES/.nupkg 一个都没碰 —— 那三样才是更新器与启动认的东西，动了会让存量安装升不上去。二，下载区先给一张「我该下哪个」的对照表，再按产品各出一张平台表；客户端那次构建没产出时整张表省略而不是印一排空格。三，客户端也有了自己的 manifest.json（scripts/desktop/build_client_manifest.py，在 _release.yml 里读回刚建好的 release 生成），服务端 AppDownloadManifestService 按 URL 拉取并缓存两份清单，GET /other-devices/downloads 一次返回两个产品。

「移动 App」页改名为 「其他设备」（/other-devices）：手机和另一台电脑是同一个问题的两个答案，用户脑子里想的是「我想在别的设备上用」。两边入口不同 —— 手机给二维码，另一台电脑给可发送的链接，因为看页面的人正坐在服务端那台机器前。页面不拼 URL，只渲染清单里的内容：拼出来的链接会在下一次改文件名时静默 404，而且没有任何东西会说。
本阶段未做的三项：/client/app/restart——一体版 /app/restart 的做法是“先孵化再停机”，而单实例互斥体由父进程持有到退出为止，孵化出的子进程很可能把父进程认成“已有实例”并直接退出，restart 就变成 quit。这条竞态在一体版里同样存在，已单独记为 #1343（互斥体行为已本地验证，桌面时序未验证），客户端不复制它——更新重启走 Velopack 自己的交接，不受影响；版本不匹配的持续提示——已补：设计文档 §4.5 要的是“持续可见、说明该升级哪一端”，握手只拦协议不兼容的硬失败，版本不同但能通信的情况此前界面什么都不说。现在侧边栏更新横幅上方多一行常驻提示，比较用的是真正的 semver 次序（2.10 新于 2.9、正式版高于自己的预发布、beta 之间可比），读不出来的版本只说“不一致”而不指认某一端；POST /client/path-mappings/resolve（按映射状态灰掉“打开目录”按钮）——它要把 ClientPathMapper 的最长前缀匹配复制到 TypeScript 里，而客户端拒绝时前端已经给出指向映射页的提示。两项都可随时补，都不挡发布。

5.4 请求签名格式（HMAC，决策 3）

Authorization: Bakabase-Device {deviceId}:{timestampSeconds}:{nonce}:{base64url(sig)}

sig = HMAC-SHA256(deviceKey, 规范串)
规范串 = "1\n" + deviceId + "\n" + METHOD + "\n" + path + "\n" + 原始查询串 + "\n" + timestamp + "\n" + nonce
         (+ "\n" + SHA-256(请求体)  仅非 GET 且请求体小于阈值，否则用空摘要)

服务端：|now - timestamp| ≤ 5 分钟；同设备同 nonce 在窗口内只接受一次（NonceCache 按设备分桶、限容）
  • 为什么放 Authorization 头而不是自定义头：UseResponseCaching 在 MVC 过滤器之前（AppStartup.cs:121），/tool/thumbnail 的 [ResponseCache] 缓存键只含 path/w/h；带 Authorization 的请求既不读也不写响应缓存，已配对设备加载过的库外缩略图才不会被匿名调用方命中。
  • 查询串必须参与签名：/file/raw?fullname= 的路径在查询串里。按原始字节签，服务端不要重新编码再比对（Dart 的 Dio 对列表参数编码为 ids=1&ids=2）。
  • 浏览器无法给 WebSocket 加头：第一版不支持"普通浏览器配对"，只有转发层与移动端是签名方（二者都能加头）。查询串签名明确排除。
  • 规范串代码 RemoteRequestSignature 是静态类，服务端验签与客户端签名用同一份；与 Dart 共用一组黄金向量测试。
  • server-info 下发 serverTime，客户端算时钟偏移后再签。

5.6 本地转发层

9.2 运行时依赖：谁连谁

三类客户端（薄客户端、手机 App、浏览器）与两处服务端承载（一体版内置、独立容器）之间是完全的多对多，没有任何一条是特殊路径。这带来一个直接结论：不需要为"在 Windows 上跑纯服务端"再造一个产物——装一体版、让它开着，它内置的那个服务端就是合法的连接目标，这也正是"一机双跑"那条决策成立的原因。

为什么做成独立产物而不是同一安装包的启动模式（决策 06）。决定性的理由不是体积——实测只省 25%（191 MB → 约 142 MB，linux-x64 自包含未裁剪；大头是 .NET 运行时、Kestrel、Avalonia/Skia，客户端一样要带）。真正的理由有三条：一，它消掉了原方案里最脆的一处改动，而那处改动本来就是错的（§5.1 陷阱一）；二，它修掉了"一机双跑"下的单实例名冲突（陷阱二）；三，"客户端不碰数据库"从纪律变成链接期保证，R2–R4 与 §6 的一串人工核对项直接变成"编译不过"。

代价是实打实的：构建矩阵 4 → 7 条腿；要开第二条更新通道（AppUpdater.cs:59-60 按 {base}/{rid}/ 取包、包标识写死 Bakabase，需要 Bakabase.Client 的标识与 releases/client/{rid}/ 前缀）；BakabaseUpdateSource 现在在 Bakabase.Service/Components/，要先搬到共享位置；用户在下载页要做一次选择，切换风味等于重装一次。
一个需要你知道的取舍：网页前端由服务端下发。按 §5.6 的路由，除了本机执行的端点和上下文接口，其余请求都转发给服务端，/ 也在其中。好处是前端版本永远和服务端一致，版本不匹配只剩客户端本机端点这一小块。代价是冷启动要过网取一次页面：入口文件被设成每次都回源校验（AppStartup.cs:176-187），带哈希的资源文件由内嵌浏览器缓存。局域网下这部分是几十毫秒量级，可以接受；如果以后要支持广域网，这里要重新算账。备选方案是前端改由本地 publish/web 提供，代价是把前端也拖进版本不匹配的范围。

10.2 一体版有两处专门为"服务端在本机"做的优化，薄客户端会失去

这是"除了服务端读写慢一点，还有没有别的损耗"的正面回答。有，而且第一条是结构性的。

其一：三端口分片

桌面版故意开三个监听端口（BakabaseHost.cs:38 的 DefaultAutoListeningPortCount => 3），封面从第二、第三个端口里随机挑一个去取（ResourceCover/index.tsx:105-114）。目的是绕开浏览器"同一个来源最多 6 条并发连接"的限制，把一页几十张封面的并发从 6 提到约 18。仓库里没有任何 HTTP/2 或加密传输配置，所以这个连接数限制是实打实的。

那段代码自己带着注释说明了为什么远程不行：服务端下发的地址被改写成 localhost，在别的设备上会指回设备自己，所以远程客户端必须退回单一来源。今天的手机端和远程浏览器就是这样，并发掉到 6。

薄客户端可以把它拿回来，而且几乎免费。转发层本来就跑在本机：让它监听三个回环端口、把这三个都报给前端即可，对上游服务端仍然只用一个连接池。前端那段判断需要区分"远程浏览器"和"薄客户端"——薄客户端不该走远程分支。建议并入阶段二，否则薄客户端的列表首屏会明显慢于一体版，而这正是用户第一眼会看到的画面。

其二：封面不带尺寸参数

前端取封面时不传宽高，服务端在没有宽高时就直接原样返回文件。自动生成的封面上限是 600×600，但手动设置或增强器抓来的封面是原始分辨率。在回环上这是零成本的偷懒；过网之后，它会成为首屏的主要字节开销。

更正：只在前端传宽高会让情况更糟，实现时才发现。一旦带上宽高，服务端会解码成 Argb32 并无条件重新编码成 PNG——即使根本不需要缩放。对照片类封面，PNG 会比源 JPEG 大好几倍。而且 ImageExtensions 里含 .svg 与 .ico，这条路径上会直接抛异常。

正确的做法是先改服务端：不重新编码的格式（.svg、.ico、.gif、.bmp、.tiff）一律原样透传；其余先只读图片头，已经够小就透传原文件，确实需要缩放时才解码，并按源格式重新编码以保持内容类型。压缩包内的缩略图同理。改完之后前端再传 600×600 才是安全的——自动生成的封面本来就没超过这个尺寸，会原样透传，字节与今天完全一致。

这一项改完，一体版、手机端、远程浏览器同样受益，且不改变任何行为，属于可以在阶段零就做掉的清理。

10.3 交互体验上的变化

  1. 断线是真的会发生，而现在界面对此毫无表示。实时推送连接没有启用自动重连，关闭回调只写日志，靠一个 5 秒轮询的守护循环重连（UIHubConnection.ts:246-271）。断开期间界面不给任何提示，各个数据仓库静默保留旧值。一体版的回环连接永远不断，所以这个缺陷今天暴露不出来；薄客户端会天天遇到。这是用户唯一会"感觉不一样"的地方，也是必须补的。
  2. 每次重连都会重放一次全量状态。初始数据是逐条 await 发出的约 34 条消息，其中 24 条是按选项类型一条条发的（WebGuiHub.cs:108-146）。回环上是几毫秒；局域网上是 34 次往返，而且每次重连都要重来。合并成一条消息是个独立的小改进，对一体版也只有好处。
  3. 启动到资源列表出现是 6 跳串行依赖：推送握手 → 已存搜索 → 搜索 → 取详情 → 发现订阅 → 封面。第 5 跳的门槛是"资源选项必须由推送送达"，也就是说列表在那 34 条消息发完之前根本不会开始加载（ResourceTabContent.tsx:155-168）。局域网下是几十毫秒，可接受；记下来即可，不构成阻塞。

10.4 结论与要做的事

一句话回答：除了每次请求多一跳网络，只有一处结构性损耗——三端口分片失效，封面并发从约 18 掉到 6，而它在薄客户端里可以还回来。其余可感知的地方，都是既有的浪费在过网之后被放大，修它们对所有形态都有好处。交互体验上真正会变的只有一件事：断线。
要做的事放在哪为什么
转发层监听三个回环端口并报给前端；前端区分远程浏览器与薄客户端阶段二补回唯一一处结构性损耗，代价接近零
把断线做成看得见的界面状态，接进前端第三态（§5.7）阶段二用户唯一会感觉到的差别；顺带修掉一体版也存在的静默陈旧
封面请求带上宽高参数阶段零纯清理，不改行为，所有形态受益
播放走路径映射阶段三命中后码流完全不经转发层；未命中退回流地址，能播但吃带宽
详情弹窗的 36 张图改用缩略图端点并加缓存头；文件浏览器逐行请求改批量接口；初始数据合并成一条消息独立立项都是既有问题，不搭本设计，但会决定薄客户端"顺不顺手"
本设计只对局域网负责。服务端没有启用响应压缩（AppStartup.cs 里只有 UseResponseCaching），传输也没有加密与 HTTP/2。局域网下这些都无所谓；广域网下每次往返 50 毫秒以上、JSON 还不压缩，上面这张表的结论要全部重算。广域网是另一个立项。
