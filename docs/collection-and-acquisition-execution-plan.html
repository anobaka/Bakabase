集合与获取流水线执行计划

配套 集合与获取流水线设计。设计文档回答「做成什么样」，本文档回答「按什么顺序、每一步改哪些文件、怎么验收」。顺序自底向上：先让未落地资源独立成立，再让它能被自动补齐，然后才是集合与订阅。

批次是执行单位：一个批次 = 一个分支 = 一个 PR = 一次可以独立验收的交付。每个批次的「改动清单」写到文件与成员级，引用的位置均已在代码中核实（行号随代码演进可能漂移，以文件与成员名为准）。每个批次的描述足以直接作为一次开发会话的任务书。工作量是单人加 AI 辅助的指示值，用于排序与切分，不是承诺。

五个里程碑

一 未落地资源独立可用 → 二 收件箱版获取流水线 → 三 集合与收集率 → 四 订阅与平台对接器 → 五 扩展。前两个里程碑不引入集合概念，完成后所有者当前的人工流程已只剩「在网盘页面点下载」。

关键路径

1.1 → 1.2 → 1.4 → 1.5 → 2.1 → 2.2 → 2.3 → 2.4 → 2.5 → 2.6 → 2.7 → 2.8。2.1（步骤契约）与 2.2（引擎扩展）可并行；其余批次可与关键路径并行；里程碑三、四只依赖里程碑一、二的产物，不依赖彼此的全部内容。

每个批次的完成定义

迁移由 dotnet ef migrations add 生成且纯 schema；yarn gen-sdk 产物已提交；新增行为有测试；中英文 i18n 齐全；dotnet build 与前端类型检查通过；偏离设计文档的决定回写到设计文档 §16。

§1工程约定（每个批次都遵守）

分支与提交

  • 一个批次一个分支，从 main 拉出，命名 feat/<里程碑>-<批次>-<短名>。
  • 提交信息英文、沿用 feat / fix / refactor / docs 前缀；一个批次合并前可以多次提交，合并用 PR。
  • 只改文档或 .claude/ 的提交加 [skip ci]；本计划的批次都含代码，不加。

数据库

  • 迁移一律 dotnet ef migrations add {Name} --project src/legacy/Bakabase.InsideWorld.Business --startup-project src/apps/Bakabase.Service --context BakabaseDbContext，纯 schema，不写 migrationBuilder.Sql。

  • 后台服务、多实现枚举注册、BTask 外壳都沿用现有模式，不引入新框架。

前端

验收

  • 用 DLsite 集成：下载并解压一个作品后手动触发同步，资源卡片从「未落地」变为可打开文件夹，封面与可播放文件正常，名称不再为空。
落地时与计划的差异。计划让落地服务调用 ResourceSyncService 上的公开包装，但同步服务同时也要调用落地服务，两个 scoped 服务互相依赖会在解析时成环。实际做法是把这两个方法从 ResourceSyncService 抽成新的 ResourceStructureService（RebuildParentChildRelationships、MarkPathMarksAsPendingForPaths），两边都依赖它，没有环。
另外两点：MergeResources 不搬运属性值（注释里写明由调用方先行处理），所以落地服务在合并前自己把自定义与保留属性值改挂到存活资源上，仅填补存活资源没有的键；同步过程中的落地不是在 ResolveResourceForEntry 里直接调用（那里是同步方法，且写库发生在之后的批量保存），而是把待落地项记录到同步上下文，批量保存后统一执行。

§7横切事项与风险控制

可见性与回滚

  • 新菜单项（获取中心、集合）标 Beta；未完成的入口不显示而不是显示后报错。
  • 每个批次的迁移只增不删（删除表推迟一个版本），保证能回退到上一版本二进制。
  • 里程碑一改动现有同步与增强逻辑，合并前用现有 DLsite / Steam 数据做一次全量同步对比资源数与名称。

花钱的动作

  • 自动购买默认关闭；2.2 之前 SoulPlusContentFetcher 的自动购买已被移除，任何购买都有 PurchaseRecordJson 与通知。

第三方页面变化

  • 读取器与提供器的解析用固定样例做回归测试；线上失败写入订阅或任务的错误字段并通知，不影响其他来源。

性能

  • 落地服务不等待全量同步；规则集合结果缓存并随事件失效；订阅检查按各自间隔而非固定 30 分钟；收件箱监听只看一层。

文档回写

  • 每个批次合并时更新设计文档 §13 的进度与 §16 的偏离记录；本计划的批次表同步勾选。

何时该停下来重新讨论

  • 1.2 的合并策略在真实库上出现非预期合并；2.5 的自动认领错误率高于人工可接受；4.1 的分享条目标题匹配产生错误合并。这三处都有「保守默认 + 人工确认」的退路，触发时先降级为人工确认再讨论算法。
  • 2.2 的引擎扩展导致现有 Workflow 测试失败且不能在改动范围内修复：切换到独立运行器宿主（§3 开头的降级路径），不扩大引擎改动。
