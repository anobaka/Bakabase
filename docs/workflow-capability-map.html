Workflow 能力全景：现状盘点与扩展路线

视角：Workflow 模块整体，而非某个场景。文件清洗是多数扩展的第一个用户，但每项扩展都是跨场景通用能力

定位（所有者 2026-09 明确）：Workflow 是 Bakabase 应用最底层的通用自动化层。三类扩展与引擎的三个插槽一一对应——任意内部事件（逐个埋点 + 一个触发器类）→ 触发器注册表；用户自定义流程（仅由已开发节点组成）→ 定义 + 链式编辑器；任意动作（写文件、写数据…，逐个开发）→ 活动注册表。引擎对节点内容不理解（payload / config 均为不透明 JSON），只做编排——这正是"逐个开发、引擎零改动"能成立的原因。候选事件/动作全景见 §6，通用化的引擎级前提见 §5 第二轮发现。

现状与结论均已在代码中逐条核实：src/modules/Bakabase.Modules.Workflow + src/apps/Bakabase.Service/Components/Workflow + 前端 src/web/src/components/Workflow。§5 记录了本轮逐行复核后与初版设计假设不符的地方，实施顺序（§8）因此有两个待选方案。

§1核心概念关系

先把引擎有哪些零件、它们怎么咬合讲清楚。现有= 代码里已经有；需新增= 六项扩展之一要加的；E1 已完成= 本轮刚加的。

1.1 定义期：用户搭出来的东西

WorkflowDefinition  [现有]          ← 用户在 workflow 页编辑器里搭出来的一条流程
  ├─ TriggerKind        "downloader.completed" / "fs.manualScan"
  ├─ TriggerFilterJson  不透明 JSON，由该触发器自己的 UI 负责读写
  ├─ Enabled            只管事件触发；手动运行不看它

§5本轮代码复核发现（与初版设计假设不符）

初版设计写作时未逐行读过引擎。第一轮（发现 1–4）修正与初版假设不符的事实；第二轮（发现 5–9）来自"通用化审计"——3 路并行代码扫描 + 一轮独立复核，复核对全部结论逐条开文件验证。每条都影响排期。

发现 1 · 引擎从未成功执行过一次运行已修复

WorkflowRunner 注入了 IServiceProvider 并把字段命名为 _rootServices，但它注册为 scoped，拿到的其实是解析它的那个 scope。三个调用方（启动时的 rehydrator、事件总线、定义服务）都把 runner 捕获进随后才执行的 BTask 闭包，那时 scope 早已释放——ExecuteAsync 第一行创建 scope 取 DbContext 就抛 ObjectDisposedException，运行还没开始就失败。
含义：既有的 subscription 与 downloader 两条业务线的工作流从来没有成功跑过。改注入 IServiceScopeFactory（始终从根容器创建，且在解析它的 scope 释放后仍可用），回归测试按真实调用形态构造：scope 内解析 → 释放 scope → 执行。issue #1251。
对计划的影响：排期的第一件事不是"加节点"，而是"证明地基能承重"——包括把两条既有业务线各跑一次真实场景，确认没有第二个同类问题。

发现 2 · 类型推导有前后端两份实现

后端 WorkflowDefinitionService.ValidateActivities 沿链追踪当前 item 类型做保存期校验；前端 chainWalk.ts + activityFit.ts 是它的手写镜像，用于 picker 筛选与即时报错。
对计划的影响：E3 能力契约要同时插进这两处。初版把 E3 当作"一次声明、整族可用"的省力方案，但它自身的接入成本是双份的，且此后每次契约演进都要同步两边。是否先把契约元数据统一由后端下发、前端只做渲染，是一个待拍板项（§9·问题 4）。

发现 3 · 两阶段运行需要第二次 schema 变更

清洗设计 §5 写的"本扩展是整个功能唯一的 schema 变更"不成立：E5 的计划表 + FileRenameRecord 是继 SpecialText 之后的第二次建表。
对计划的影响：E5 不是纯逻辑扩展，排期要按"带迁移的批次"估。计划存独立表还是塞进 WorkflowRun 的 JSON 字段，是一个待拍板项（§9·问题 3）。

发现 4 · 链中展开比预估便宜

WorkflowRunStepStat 已经是 InputCount / OutputCount 两个独立计数，天然能表达 1→N，统计模型不需要改（初版把它列为开放问题）。实际要改的只有 WorkflowItemOutcome（一个 readonly record struct）和 runner 的 per-item 循环。
对计划的影响：E2 可以排得比原计划更靠前或更靠后都不痛，它不再是重活。

第二轮：通用化审计（引擎作为应用级自动化层的前提）

发现 5 · 活动配置解析失败被静默吞成默认值

WorkflowExecutionContext.GetConfig<T>（:40-45）对坏 JSON 做 catch (JsonException) { return default; }——配置损坏/过期的节点按默认配置执行，任何地方都不报错。既有过滤器在默认配置下刻意"全量放行"（怕误删），于是：坏的过滤器配置 → 无声放行全部条目 → 下游若是写盘动作，就在未过滤的集合上执行。同族问题：payload 属性改名后，存量 Pending run 反序列化时该字段静默变 null（System.Text.Json 忽略未知成员）。
对"任意动作"的含义：破坏性动作开闸前，配置解析失败必须从"默默用默认值"改成"运行失败并说明原因"。

发现 6 · 整个 run 共享一个 DI scope 和一个 DbContext

WorkflowRunner.ExecuteAsync 为整个 run 建一个 scope（:51-52），每个 item 的 ctx.Services 都是它——活动解析到的 scoped 服务（DbContext 在内）与 runner 共享实例。后果：活动里任何 SaveChangesAsync 都会提前刷出 runner 正在跟踪的 run/definition 行；长运行的 change tracker 随 items × steps 无界增长；活动把 context 弄脏会毒化 runner 自己 finally 里的收尾保存（run 卡 Running → 下次启动变 Interrupted）。
对"任意动作"的含义：写数据类动作要么在自己的子 scope 里干活，要么 runner 改为 per-item scope——二选一，不能放任。

发现 7 · 运行时 item 是未校验的 object；AI 节点把 LLM 文本直接变成带类型的 item

类型标签只在保存期校验；运行时 runner 从不核对 item 的 CLR 类型与链上声明是否一致，具体活动各自防御——且防御方式是"类型不符默默放行（KeepItem）"而非丢弃。三个不同标签共享同一个 ClrType（SubscriptionAny/PixivIllust/ExHentaiGallery → SubscriptionItem），AI 节点按 ClrType 反查描述符时"多标签共 CLR 型时是模糊的"，其输出路径是把 LLM 原文 JsonSerializer.Deserialize 成目标 ClrType——幻觉出来的字段值就成了全类型化的 item。今天它变成一个真实下载任务；通用层里它会变成文件删除或数据更新的目标，LLM 与副作用之间没有任何校验闸门。（AiTransformActivity.cs:91-104）

发现 8 · 事件内联发布、无事件日志、不匹配即永久丢弃

生产者在自己的调用路径上 await PublishAsync（今天仅 2 个埋点：DownloadTaskService.cs:231、SubscriptionService.cs:206）——每个事件都在生产者路径上做一次定义查询 + 可能的写行，bus/DB 异常会打回生产者。matched.Count == 0 → return：没人订阅的事件不落任何痕迹，事后创建/启用的定义永远看不到它；定义的过滤器抛异常只 LogWarning 跳过，该定义会无限期静默错过事件且 LastError 不被设置。
对"任意事件"的含义：埋点铺开之前要决定——高频事件（属性变更、文件扫描）是否需要节流/离线队列，以及"我的自动化没触发"要不要留取证轨迹。

发现 9 · 定义变更没有在途保护

DeleteAsync 是三个裸 ExecuteDeleteAsync（活动、runs、定义），不检查是否有在途 run——删除后在途 run 继续执行副作用，收尾保存落在已删除的行上。runner 在执行时现读活动链（:95-98）——先排队后编辑，等于旧 payload 跑新链。ExecuteAsync 不复查 Enabled——禁用定义不撤销已排队的 run（只有重启后的 rehydrator 会过滤）。
对用户的含义：发现一条破坏性链在乱跑 → 点禁用（排队中的照跑）或删除（在途的继续写盘），用户合理地以为已经停住了，实际没有。

§7串联视角：扩展如何互相成立

  • 手动触发 + 链中展开 + 变量组合出"手动对文件系统跑多层级联动流程"（清洗的骨架）；
  • 能力契约使 text 节点族对任何未来 item 类型开放（画廊标题清洗零成本）；
  • 两阶段运行是所有落盘类 action 的安全模型，与手动触发组合出"手动预览-确认"的标准交互；
  • 定时/监听触发 + 既有 downloader.completed 触发器 + fs/text 节点 = "下载完成 → 自动清洗 → 通知"全自动链，届时引擎零新增。
