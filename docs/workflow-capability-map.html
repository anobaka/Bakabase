Workflow 能力全景：现状盘点与扩展路线

视角：Workflow 模块整体，而非某个场景。文件清洗是多数扩展的第一个用户，但每项扩展都是跨场景通用能力

现状与结论均已在代码中逐条核实：src/modules/Bakabase.Modules.Workflow + src/apps/Bakabase.Service/Components/Workflow + 前端 src/web/src/components/Workflow。§4 记录了本轮逐行复核后与初版设计假设不符的地方，实施顺序（§7）因此有两个待选方案。

§0代号速查

下面六项引擎扩展在几份文档里都用 E1–E6 互相引用。代号只是索引，含义以名称为准：

代号名称一句话状态

E3能力契约节点声明"我要能改文本的东西"，而不是逐个列举类型未做

§4本轮代码复核发现（与初版设计假设不符）

初版设计写作时未逐行读过引擎。下面四条是逐行复核后修正的事实，每条都影响排期。

发现 1 · 引擎从未成功执行过一次运行已修复

WorkflowRunner 注入了 IServiceProvider 并把字段命名为 _rootServices，但它注册为 scoped，拿到的其实是解析它的那个 scope。三个调用方（启动时的 rehydrator、事件总线、定义服务）都把 runner 捕获进随后才执行的 BTask 闭包，那时 scope 早已释放——ExecuteAsync 第一行创建 scope 取 DbContext 就抛 ObjectDisposedException，运行还没开始就失败。
含义：既有的 subscription 与 downloader 两条业务线的工作流从来没有成功跑过。改注入 IServiceScopeFactory（始终从根容器创建，且在解析它的 scope 释放后仍可用），回归测试按真实调用形态构造：scope 内解析 → 释放 scope → 执行。issue #1251。
对计划的影响：排期的第一件事不是"加节点"，而是"证明地基能承重"——包括把两条既有业务线各跑一次真实场景，确认没有第二个同类问题。

发现 2 · 类型推导有前后端两份实现

后端 WorkflowDefinitionService.ValidateActivities 沿链追踪当前 item 类型做保存期校验；前端 chainWalk.ts + activityFit.ts 是它的手写镜像，用于 picker 筛选与即时报错。
对计划的影响：E3 能力契约要同时插进这两处。初版把 E3 当作"一次声明、整族可用"的省力方案，但它自身的接入成本是双份的，且此后每次契约演进都要同步两边。是否先把契约元数据统一由后端下发、前端只做渲染，是一个待拍板项（§8·问题 4）。

发现 3 · 两阶段运行需要第二次 schema 变更

清洗设计 §5 写的"本扩展是整个功能唯一的 schema 变更"不成立：E5 的计划表 + FileRenameRecord 是继 SpecialText 之后的第二次建表。
对计划的影响：E5 不是纯逻辑扩展，排期要按"带迁移的批次"估。计划存独立表还是塞进 WorkflowRun 的 JSON 字段，是一个待拍板项（§8·问题 3）。

发现 4 · 链中展开比预估便宜

WorkflowRunStepStat 已经是 InputCount / OutputCount 两个独立计数，天然能表达 1→N，统计模型不需要改（初版把它列为开放问题）。实际要改的只有 WorkflowItemOutcome（一个 readonly record struct）和 runner 的 per-item 循环。
对计划的影响：E2 可以排得比原计划更靠前或更靠后都不痛，它不再是重活。

§6串联视角：扩展如何互相成立

  • 手动触发 + 链中展开 + 变量组合出"手动对文件系统跑多层级联动流程"（清洗的骨架）；
  • 能力契约使 text 节点族对任何未来 item 类型开放（画廊标题清洗零成本）；
  • 两阶段运行是所有落盘类 action 的安全模型，与手动触发组合出"手动预览-确认"的标准交互；
  • 定时/监听触发 + 既有 downloader.completed 触发器 + fs/text 节点 = "下载完成 → 自动清洗 → 通知"全自动链，届时引擎零新增。

§7实施顺序：两个待选方案

前置的 SpecialText 扩展已完成，手动触发（E1）已完成。之后的顺序有两个方案，尚未拍板。

方案 A · 按引擎能力横切（初版顺序）

能力契约 + 变量（E3+E4，text 节点按清洗设计规范生而通用，与变量机制同批落地）→ 链中展开（E2）→ 两阶段运行（E5）。定时/监听（E6）独立排期。

优点：每批是一个完整的通用能力，概念干净。缺点：落盘与撤销（E5）排在最后，所以在全部做完之前用户一次也用不上这个功能，中间几批也无法用真实场景验收。

方案 B · 薄纵切（复核后建议）

先打通最窄的一条端到端链，再逐步加宽。判据是每批结束时用户能做什么：

批次主题内容做完之后用户能做什么
0地基已完成runner scope 修复（发现 1）+ 手动触发（E1）；建议补一步：把两条既有业务线各跑一次真实场景能手动跑一条工作流并看到它成功
1最小纵切fs.manualScan 触发器 + transform.fs.fileNameOp（直接包既有 FileNameModifier，不依赖能力契约与变量）+ action.fs.saveName 只做 Preview选目录 → 看到改名预览
2落盘（E5）计划表 + Apply + FileRenameRecord + 撤销功能真正可用：预览 → 确认 → 落盘 → 可撤销
3文本族（E3）能力契约 + transform.text.removeWrapped / removeTexts / trim清洗能力变强（词表驱动地删噪声）
4联动（E4+E2）变量随行袋 + capture / template + expand.fs.children多层级、跨层级信息组合命名（13 节点示例的完整形态）
5自动化（E6）cron / 目录监听触发下载完成 → 自动清洗
核心理由：没有 Apply 的清洗流程是玩具，所以两阶段运行必须提前到第 2 批；能力契约与变量是"让它更强"，不是"让它可用"，可以后置。代价：fileNameOp 先落在 fs 域、text 节点族晚一批到——而这两者本来就是设计里刻意分开的两条线（见清洗设计 §3.0），不构成返工。
